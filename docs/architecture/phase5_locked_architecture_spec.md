## 3. Identity Model

Identity in KORTEX Phase 5 consists of two distinct, coupled authority chains:

### Conceptual Authority Chain
```
Persistent Machine Installation ID (Windows Registry)
          │
          ▼
      Agent Identity (Principal Type = AGENT)
          │
          ▼
    PrincipalRecord (Authoritative Database Record)
          │
          ▼
        Tenant (Authoritative Database Column)
```

### Cryptographic Identity Chain
```
Agent Private Key (Local Windows CNG Store, Non-Exportable)
          │
          ▼
Certificate Signing Request (CSR)
          │
          ▼
    Internal KORTEX Root CA
          │
          ▼
 Client X.509 Certificate (Subject CN = PrincipalRecord.principal_id)
          │
          ▼
  mTLS Authenticated Session
```

**Identity Rules**:
1. `MachineInstallationId` is an installation identifier and database binding attribute. It is NOT a cryptographic authentication factor and NOT hardware attestation.
2. The client private key and X.509 certificate constitute the exclusive cryptographic authentication factor.
3. The backend database `PrincipalRecord` is the sole authority for tenant binding (`tenant_id`) and lifecycle state (`enabled`).
4. Tenant identity is never derived from the client and never accepted from client claims.

## 4. Machine Installation ID

- **Name**: Persistent Machine Installation ID.
- **Format**: Canonical 36-character UUIDv4 string (`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`).
- **Generation**: Generated locally by the Desktop Agent upon first launch using a cryptographically secure RNG (`Guid.NewGuid().ToString("D")`).
- **Storage Hive**: `HKEY_LOCAL_MACHINE`.
- **Exact Registry Path**: `HKLM\SOFTWARE\KORTEX\Agent`.
- **Exact Registry Value**: `MachineInstallationId`.
- **Value Type**: `REG_SZ`.
- **Access Control**: Local SYSTEM and Administrators have Full Control; Agent Service account has Read and initial Write permissions.
- **Persistence**: Survives application restarts, service restarts, OS reboots, and application upgrades.
- **Replacement / Modification**: Manual replacement or deletion of this key invalidates the local installation binding; the agent will fail the `AgentStatus` binding verification and be rejected by the Gateway until re-enrolled.

---

## 5. Principal/Tenant Model

- Every enrolled agent is represented by a row in `security_principals` (`PrincipalRecord`):
  - `principal_id`: UUIDv4 string generated by the backend during enrollment.
  - `principal_type`: `"AGENT"` (`PrincipalType.AGENT.value`).
  - `tenant_id`: String derived exclusively from the enrollment token record.
  - `enabled`: Boolean (`True` for active, `False` for disabled).
  - `machine_installation_id`: Canonical UUIDv4 string matching the agent's Registry value.
- **Database Constraint**: `UniqueConstraint("machine_installation_id", name="uq_security_principals_machine_id")` ensures a 1:1 mapping between active installations and principals.
- Cross-tenant reuse is prevented because `machine_installation_id` is globally unique across the entire `security_principals` table.

---

## 6. Enrollment Token Model

- **Token Generation**: 32 cryptographically secure random bytes generated via `secrets.token_bytes(32)`. Distributed to the administrator as a 64-character lowercase hexadecimal string (`secrets.token_hex(32)`).
- **Hashing Algorithm**: SHA-256 exclusively.
- **Storage**: Only the 64-character hex digest of `SHA-256(raw_token)` is persisted.
- **Raw Token Secrecy**: Raw tokens are never persisted, never written to disk, never logged, and never returned in API responses after generation.
- **Token Validity**: 24 hours from creation (`expires_at = created_at + timedelta(hours=24)`).
- **Single-Use Semantics**: An enrollment token can successfully complete enrollment exactly once.

---

## 7. Enrollment State Machine

The enrollment state machine uses four mutually exclusive states evaluated from database fields:

```
            ┌─────────────────────┐
            │   TOKEN_AVAILABLE   │
            └──────────┬──────────┘
                       │
         ┌─────────────┴─────────────┐
         │                           │
         ▼                           ▼
[Valid Enrollment]            [now >= expires_at]
         │                           │
         ▼                           ▼
┌──────────────────┐       ┌───────────────────┐
│  TOKEN_RESERVED  │       │   TOKEN_EXPIRED   │
└────────┬─────────┘       └───────────────────┘
         │
         ▼
[DB Commit + Cert Stored]
         │
         ▼
┌──────────────────────┐
│ ENROLLMENT_COMPLETED │
└──────────────────────┘
```

**State Definitions**:
- `TOKEN_AVAILABLE`: `consumed_at IS NULL` AND `now < expires_at`.
- `TOKEN_RESERVED`: Token row locked `FOR UPDATE` within active database transaction.
- `ENROLLMENT_COMPLETED` iff ALL are present:
  - `consumed_at IS NOT NULL`
  - `enrollment_principal_id IS NOT NULL`
  - `enrollment_csr_hash IS NOT NULL`
  - `enrollment_machine_installation_id IS NOT NULL`
  - `issued_certificate IS NOT NULL`
  - `certificate_fingerprint IS NOT NULL`
- `TOKEN_EXPIRED`: `consumed_at IS NULL` AND `now >= expires_at`.

*Note: Partially populated enrollment records are never treated as completed. If a partial state exists, it implies database invariant violation and forces a fail-closed response.*

## 8. Enrollment Transaction Boundaries

The enrollment REST endpoint (`POST /api/v1/agent/enroll`) executes within a strict transactional sequence:

1. **Begin Database Transaction**.
2. **Lock Token**: `SELECT * FROM security_agent_enrollment_tokens WHERE token_hash = :hash FOR UPDATE`.
3. **Validate Existence**: If row not found, raise HTTP 403 Forbidden.
4. **Compute Hashes**: Calculate `csr_hash = sha256(csr_bytes).hexdigest()`.
5. **Check Completed Enrollment (Idempotency Branch)**:
   - If enrollment is already COMPLETED (all 6 completed state fields are NOT NULL):
     - Compare `enrollment_csr_hash` to `csr_hash`.
     - Compare `enrollment_machine_installation_id` to the submitted MachineInstallationId.
     - If BOTH match: Return the exact stored `issued_certificate` (HTTP 200 OK).
     - If either differs: Raise HTTP 403 Forbidden.
     - *DO NOT perform expiration validation for this completed-enrollment recovery path.*
   - If partially populated state exists (e.g., `consumed_at IS NOT NULL` but missing certificate): Raise fatal error (fail closed), produce audit event, do not return certificate.
6. **New Enrollment Branch (If enrollment is NOT completed)**:
   - **Validate Expiration**: If `now >= expires_at`, raise HTTP 403 Forbidden.
   - **Validate Machine ID Uniqueness**:
     - Check `SELECT id FROM security_principals WHERE machine_installation_id = :machine_id`.
     - If found: Raise HTTP 409 Conflict.
   - **Reserve Token**: Set `consumed_at = datetime.now(UTC)`, `enrollment_csr_hash = csr_hash`, `enrollment_machine_installation_id = submitted_machine_id`.
   - **Generate Principal ID**: Generate `principal_id = str(uuid.uuid4())`.
   - **Create PrincipalRecord**:
     - `tenant_id = token_record.tenant_id`
     - `principal_id = principal_id`
     - `principal_type = "AGENT"`
     - `enabled = True`
     - `machine_installation_id = submitted_machine_id`
     - `roles = ["agent"]`
     - `attributes = {"enrolled_at": datetime.now(UTC).isoformat()}`
   - **Sign CSR**:
     - Invoke internal PKI module synchronously in-process.
     - Set Subject `CN = principal_id`.
     - Set EKU = `clientAuth`.
     - Sign with CA private key loaded from SecretStore.
     - Produces `cert_pem_bytes` and `cert_fingerprint = sha256(cert_der_bytes).hexdigest()`.
   - **Store Certificate in Token Record**:
     - Set `enrollment_principal_id = principal_id`.
     - Set `issued_certificate = cert_pem_bytes`.
     - Set `certificate_fingerprint = cert_fingerprint`.
   - **Commit Database Transaction**.
7. **Return Certificate**: Return HTTP 200 OK with `cert_pem_bytes`.

*Failure Boundary: If any exception occurs prior to Step 6 completion (including CSR parsing or cryptographic signature failure), the database transaction rolls back. The token remains in `TOKEN_AVAILABLE` state.*

---

## 9. Enrollment Idempotency

- **Same Token + Same CSR + Same MachineInstallationId**: Returns the previously issued certificate byte-for-byte. Token expiration does not apply to this recovery path. No new `PrincipalRecord` is created.
- **Same Token + Different CSR**: Rejection with HTTP 403 Forbidden.
- **Same Token + Different MachineInstallationId**: Rejection with HTTP 403 Forbidden.
- **Same MachineInstallationId + Different Token**: Rejection with HTTP 409 Conflict due to `uq_security_principals_machine_id` if an active PrincipalRecord already owns it.
- **Concurrent Enrollment Requests**: Database row lock (`FOR UPDATE`) forces sequential execution. The first transaction creates the record and commits; the second transaction reads the committed row and executes the idempotency check. Exactly one `PrincipalRecord` is created. Exactly one certificate is issued for that enrollment.

---

## 10. Enrollment Crash Recovery

- **Crash Before Commit**: Transaction rolls back. Token remains `TOKEN_AVAILABLE`. No orphaned records exist.
- **Crash After Commit, Before Response Received**: Client retries with identical `(Token, CSR, MachineInstallationId)`. Server matches `enrollment_csr_hash` and `enrollment_machine_installation_id` and returns `issued_certificate`. Idempotent recovery. Token expiration is explicitly bypassed for recovery.
- **Crash During CSR Signing**: Transaction rolls back. Token remains available for retry.
- **Crash After Response Delivered**: Client stores certificate. Subsequent retries return the stored certificate.

## 11. Internal CA / PKI

- **CA Initialization**: Explicit administrative CLI invocation:
  ```bash
  python -m kortex.engines.security.cli pki init
  ```
- **CA Overwrite Protection**: If `system/pki/ca_private_key` already exists in `SecretStore`, `pki init` aborts with an error. It never silently overwrites an existing CA.
- **Key Algorithm**: RSA 4096.
- **Basic Constraints**: `critical=True, CA=True`.
- **Key Usage**: `critical=True, keyCertSign=True, cRLSign=True`.
- **Validity**: 10 years (3650 days).
- **Subject**: `CN=KORTEX Internal Root CA, O=KORTEX, OU=Security Engine`.
- **Private Key Storage**: `SecretStore` under `tenant_id="__system__"`, `secret_handle="system/pki/ca_private_key"`.
- **Public Certificate Storage**: Persisted in `SecretStore` under `tenant_id="__system__"`, `secret_handle="system/pki/ca_public_certificate"` and written to disk at `backend/data/pki/kortex_root_ca.crt`.
- **Missing CA Failure**: If the CA certificate or key is missing from `SecretStore` during Gateway startup, the Gateway crashes immediately with a fatal log event (Fail Closed).

## 12. Server Certificate Profile

- **Basic Constraints**: `critical=True, CA=False`.

- **Issuer**: KORTEX Internal Root CA.
- **Issuance Command**:

- **Storage**: Private key in `SecretStore` (`tenant_id="__system__"`, `secret_handle="system/pki/gateway_server_private_key"`). Certificate in `SecretStore` (`tenant_id="__system__"`, `secret_handle="system/pki/gateway_server_certificate"`).
- **Hostname Verification**: The Desktop Agent enforces standard TLS hostname verification against the SAN.

## 17. Agent Gateway

- **Technology**: Python `grpc.aio.server`.
- **TLS Configuration**: `grpc.ssl_server_credentials` configured with:
  - Root CA: KORTEX Internal Root CA public certificate.
  - Server Certificate & Private Key: Loaded from `SecretStore`.
  - Client Authentication: `require_client_auth=True`.
- **Responsibilities**:
  1. Terminate mutual TLS.
  2. Cryptographically validate the client certificate chain against the Root CA.
  3. Extract `principal_id` from the client certificate's Subject Common Name (`CN`).
  4. Query `security_principals` for `PrincipalRecord` matching `principal_id`.
  5. Validate `principal_type == "AGENT"`.
  6. Validate `enabled == True`.
  7. Resolve authoritative `tenant_id` from the database record.
  8. Track active session in memory.
  9. Maintain bidirectional gRPC stream.
- **Strict Non-Responsibilities**: The Gateway does not execute capabilities, parse capability payloads, execute shell commands, or invoke `CapabilityDispatcher`.

---

## 18. Lifecycle Authorization

The Gateway enforces a two-layer security check:

- **Layer 1 (Cryptographic TLS Handshake)**: Handled by OpenSSL / gRPC. Validates signatures, expiration, trust chain, and `clientAuth` EKU.
- **Layer 2 (KORTEX Authorization Check)**: Handled in the gRPC interceptor / stream handler:
  ```python
  principal = await data_store.get(PrincipalRecord, principal_id)
  if principal is None or principal.principal_type != "AGENT" or not principal.enabled:
      context.abort(grpc.StatusCode.UNAUTHENTICATED, "Agent identity is disabled or revoked.")
  ```
  Possession of a cryptographically valid certificate without an enabled database record results in immediate disconnection.

---

## 19. Active Session Revocation

- **Mechanism**: Periodic lifecycle monitor running inside the Gateway process every 5 seconds.
- **Operation**:
  1. Every 5 seconds, the monitor queries `security_principals` for the status of all currently connected `principal_id` sessions.
  2. If any connected principal has `enabled == False` or has been deleted from the database:
     - The Gateway cancels the active gRPC stream with status `UNAUTHENTICATED`.
     - The network socket is closed.
     - A security audit event is written to `AuditManager`.
     - The session is evicted from active session memory.

## 20. Desktop Agent

- **Framework**: C# .NET 8 (targeting `net8.0`).
- **Binary Type**: Headless background console application / Windows Service.
- **Project Location**: `apps/desktop-agent/KortexAgent.csproj`.
- **Execution Flow**:
  1. Open `HKLM\SOFTWARE\KORTEX\Agent`. If `MachineInstallationId` exists, read it; otherwise, generate a new UUIDv4 and write it.
  2. Load CA public certificate from `C:\Program Files\KORTEX\Agent\certs\kortex_root_ca.crt`.
  3. Query `Cert:\LocalMachine\My` for an enrolled certificate with Subject `CN=<principal_id>`.
  4. If certificate not found:
     - Require `--token <enrollment_token>` CLI flag.
     - Generate RSA 2048 keypair in CNG (`ExportPolicy = None`).
     - Create CSR.
     - Submit `(Token, CSR, MachineInstallationId)` to `POST https://<backend>/api/v1/agent/enroll`.
     - Import returned certificate into Windows Certificate Store and associate with private key.
  5. Configure `GrpcChannel` with `HttpClientHandler` containing the loaded client certificate and custom trust root validation.
  6. Call `Connect()` bidirectional stream.
  7. Transmit `AgentMessage { status = AgentStatus { machine_installation_id = ..., status = "ONLINE" } }`.
  8. Await `GatewayMessage { session_ack = SessionAck { session_id = ... } }`.
  9. Maintain stream loop; on disconnection, enter reconnect loop with exponential backoff (1s, 2s, 4s, 8s, 16s, 32s, max 60s).
  10. On SIGTERM / SIGINT, cancel stream gracefully and shut down.

## 21. Minimal gRPC Contract

Proto file location:
- `backend/src/kortex/engines/agent_gateway/protos/agent.proto`
- `apps/desktop-agent/protos/agent.proto`

```protobuf
syntax = "proto3";

package kortex.agent.v1;

option csharp_namespace = "Kortex.Agent.V1";

service DesktopAgentGateway {
  // Bidirectional stream establishing the authenticated agent session
  rpc Connect(stream AgentMessage) returns (stream GatewayMessage);
}

message AgentMessage {
  oneof payload {
    AgentStatus status = 1;
  }
}

message GatewayMessage {
  oneof payload {
    SessionAck session_ack = 1;
  }
}

message AgentStatus {
  string machine_installation_id = 1;
  string status = 2; // "ONLINE"
}

message SessionAck {
  string session_id = 1;
}
```

*Invariants*:
- No `CapabilityRequest`, `CapabilityResult`, `ExecuteCommand`, `RunProcess`, or shell messages exist in this contract.

## 24. Failure / Fail-Closed Semantics

| Condition | Immediate Outcome | Security Action |
|---|---|---|
| CA key missing from SecretStore | Gateway aborts boot | Fail closed |
| CA key corrupted / tag mismatch | Gateway aborts boot | Fail closed |
| Server certificate missing | Gateway aborts boot | Fail closed |
| Server certificate expired | Agent rejects TLS handshake | Fail closed |
| Client certificate expired | Gateway rejects TLS handshake | Fail closed |
| Client certificate self-signed / untrusted | Gateway rejects TLS handshake | Fail closed |
| Client certificate lacks clientAuth EKU | Gateway rejects TLS handshake | Fail closed |
| Subject CN not in `security_principals` | Gateway rejects stream (UNAUTHENTICATED) | Fail closed |
| `PrincipalRecord.enabled == False` | Gateway rejects stream (UNAUTHENTICATED) | Fail closed |
| `PrincipalRecord.principal_type != "AGENT"` | Gateway rejects stream (UNAUTHENTICATED) | Fail closed |
| Database unavailable during mTLS connection | Gateway rejects stream (UNAVAILABLE) | Fail closed |
| Enrollment token expired | Enrollment API returns 403 Forbidden | Reject |
| Enrollment token hash not found | Enrollment API returns 403 Forbidden | Reject |
| Token used with different CSR | Enrollment API returns 403 Forbidden | Reject |
| Token used with different Machine ID | Enrollment API returns 403 Forbidden | Reject |
| Duplicate Machine ID on new enrollment | Enrollment API returns 409 Conflict | Reject |
| Partially populated enrollment state | Enrollment API aborts transaction | Fail closed |
| Active session principal disabled in DB | Session terminated within 5 seconds | Evict session |
| Active session principal deleted from DB | Session terminated within 5 seconds | Evict session |
| Client attempts to specify tenant in RPC | Claim ignored; DB tenant enforced | Isolation preserved |
| Server hostname does not match SAN | Agent terminates connection | Reject |

## 25. Threat Model

| Threat | Attack Vector | Mitigation Control | Expected Result |
|---|---|---|---|
| **Token Theft / Replay** | Attacker intercepts used token and attempts enrollment with own CSR or Machine ID | `enrollment_csr_hash` and `enrollment_machine_installation_id` comparison | HTTP 403 Forbidden |
| **Token Race Condition** | Attacker submits token concurrently from two machines | Row lock `SELECT FOR UPDATE` + unique machine ID constraint | Exactly one principal created |
| **Private Key Theft** | Malicious local process attempts to export agent private key | Windows CNG `CngExportPolicies.None` | Key export blocked by OS |
| **Tenant Impersonation** | Agent sends spoofed `tenant_id` in gRPC metadata | Gateway ignores client claims; loads tenant from `PrincipalRecord` | Request bounded to DB tenant |
| **Revocation Bypass** | Revoked agent uses valid certificate to maintain stream | 5-second polling monitor cancels stream on `enabled == False` | Disconnected within 5s |
| **CA Key Extraction** | Attacker attempts to read CA key from disk | Key exists only in `SecretStore` encrypted with AES-256-GCM | No plaintext key on disk |
| **Arbitrary Command Execution** | Attacker injects shell payload into gRPC stream | `agent.proto` contains no execution message fields | Serialization rejection |

## 32. Phase 5 Acceptance Criteria

1. `MachineInstallationId` is persistently stored in `HKLM\SOFTWARE\KORTEX\Agent`.
2. `MachineInstallationId` has an enforced database unique constraint across principals.
3. Enrollment token is stored as a SHA-256 digest and is strictly single-use for new enrollments.
4. Concurrent enrollment requests with the same token result in exactly one principal.
5. Retrying enrollment with the same token, same CSR, and same MachineInstallationId idempotently returns the original certificate, bypassing token expiration.
6. Retrying enrollment with the same token and a different CSR fails with HTTP 403.
7. Retrying enrollment with the same token and a different MachineInstallationId fails with HTTP 403.
8. A partially completed or corrupt enrollment state is never treated as successfully completed and causes fail-closed.
9. CA is explicitly initialized and cannot be silently overwritten.
10. CA and server private keys are protected by SecretStore, encrypted at rest, never logged, and never exposed to clients.
11. Server certificate enforces hostname verification against SAN.
12. Desktop Agent private key is non-exportable in Windows Certificate Store.
13. Desktop Agent private key is never transmitted to the backend.
14. Gateway enforces client certificate authentication (`require_client_auth=True`).
15. Gateway maps certificate Subject CN to `PrincipalRecord.principal_id`.
16. Gateway derives tenant identity exclusively from `PrincipalRecord.tenant_id`.
17. Disabled (`enabled=False`) or deleted principals cannot establish mTLS sessions.
18. Active sessions for disabled or deleted principals are severed within 5 seconds.
19. Gateway and gRPC contracts contain zero capability execution paths.
20. `backend/src/kortex/core/dispatch.py` remains untouched.
21. Phase 1–4 `python_exec` remains untouched.
22. All 35 adversarial tests pass.
