M7.4 is not defined anywhere in the repository. This pass re-verified the security finding from the prior planning pass **directly against current HEAD** and found it is **broader than previously stated**: of Document Engine's 9 capabilities, **4 have no tenant-identity verification at all** — not 2-3 as first estimated. `execute_profile` and `bind_template` trust a caller-supplied `tenant_id` field; `transition_lifecycle` and `analyze_document_intelligence` accept no tenant identifier whatsoever. **Recommended minimum product slice**: AI-triggered document generation from an existing template via `execute_profile`, governed exactly like M7.3's mutating connector tool, plus one read tool. Full reasoning in §10-11.

## 7. AI Architecture

Not re-derived from scratch (per the token-efficiency mandate — this is exhaustively documented in `docs/architecture/m7.3_connector_integration_implementation_report.md`, this session's own prior output, cross-checked rather than reread wholesale):

1. **Same `ToolRegistry`**: yes — a single, process-wide, engine-agnostic registry; no reason to create a second one.
2. **Separate read/mutation tools**: yes, mirroring M7.3's `connector_read_status`/`connector_send_action` split exactly — `is_mutation` classification is per-tool, not per-engine.
3. **Which capabilities become tools**: see §12 (AI Tool Matrix) — a minimum of one read tool (`template.list`) and one mutation tool (`operation.execute`), not all 9.
4. **Mutation-gated tools**: `operation.execute` (`is_mutation=True`); `template.list` stays `is_mutation=False`.
5. **Tool schemas**: must match each target handler's real signature exactly — `execute_profile(profile_id: str, request: OperationRequest)` takes two parameters (one nested `request` object plus a flat `profile_id`), a *different* shape from Connector's single-`request`-parameter pattern and from `transition_lifecycle`'s four-flat-parameters pattern. Each tool's schema must be independently derived from its target method, not assumed uniform (the exact mistake the M7.3 plan made and had to correct mid-implementation — flagged explicitly here to avoid repeating it).
6. **Permission per tool**: `document:read` for the list tool, `document:execute` for the mutation tool — both already exist, no new permission strings needed (unlike M7.3, which needed a new `security:secret:write`).
7. **Tenant identity handling**: **cannot simply mirror M7.3** — Connector's `execute_action` already had the principal-authoritative pattern before M7.3 touched it (M6.3-1 fixed it earlier). Document Engine's equivalent handlers do not have this yet (§8) — it must be built as part of this milestone, not merely relied upon.
8. **Error propagation**: unchanged, generic — `AIToolInvoker`'s existing `ToolExecutionStatus` (`SUCCESS`/`DENIED`/`INVALID_ARGUMENTS`/`NOT_FOUND`/`EXECUTION_ERROR`/`TIMEOUT`) already covers every Document-side failure mode without new error types.
9. **Approval context generation**: unchanged, generic — `KernelDurableApprovalBridge` builds the same `context_snapshot` shape (`action: "ai_tool_invocation"`, `task_id`, goal, proposed tool calls) regardless of which engine the mutating tool targets.
10. **Approval Queue rendering**: unchanged — `ApprovalQueue.tsx` already renders generic `tool_name`/`args` pairs and AI-vs-human requester labeling; it has no engine-specific branching to add to.
11. **Does existing approval infra already support it**: **Yes, fully** — nothing new required.
12. **Is new approval infrastructure necessary**: **No.**

## 8. Security Audit

Independently re-verified against current HEAD this pass (not carried forward as assumption):

- **Affected capabilities**: `execute_profile` (trusts `OperationRequest.tenant_id`), `bind_template` (trusts `BindingContext.tenant_id`), `transition_lifecycle` (no tenant identifier of any kind — the most severe case, since it can publish/archive a version given only a `document_id`/`version_id`), `analyze_document_intelligence` (no tenant identifier — a confidentiality risk, not just an integrity one, since it reads and returns document content-derived analysis). Four of nine capabilities, not the two-to-three estimated in the prior pass.
- **Does dispatcher injection already provide `principal`**: yes, generically, to any handler that declares a `principal` kwarg (confirmed by the Kernel dispatch mechanism M7.3 already relied on) — **none of Document Engine's handlers declare one**, so the Kernel never injects it; this is a Document-Engine-side omission, not a platform limitation.
- **Does the engine correct tenant identity anywhere**: no — grep of `document/engine.py` for `principal` returns zero matches.
- **Read capabilities with the same issue**: `preview.generate`, `intelligence.analyze` (already counted above as a mutation-adjacent case for its persisted model), `recommendation.get` — all three lack tenant scoping; `adapter.list`/`template.list` are legitimately tenant-agnostic by design (platform catalogs), and are **not** part of this gap.
- **Frontend exposure today**: the existing `document-knowledge` desktop app only calls the two legitimately-tenant-agnostic capabilities — **the vulnerable path is not currently reachable from the desktop UI**, only from any direct authenticated capability caller. This matters for severity (not yet actively exploited through a shipped UI) but not for classification (still a real, live gap for any API client, and would become AI-agent-reachable the moment this milestone's tools are added).
- **Test coverage of cross-tenant access**: none, confirmed by grep (`cross_tenant`/`cross.tenant` return zero hits in any `test_document*.py` file) — this is precisely why the gap went undiscovered until this planning pass.

**Classification: BLOCKING FOR M7.4.** Justification: this milestone's entire purpose is to make these specific capabilities reachable by an LLM-driven agent. Shipping that reachability on top of an unverified tenant boundary would let a cross-tenant AI agent — or, more mundanely, a single misconfigured/compromised session — mutate or read another tenant's document data by supplying a different id. It is not blocking in the sense of "abandon the milestone" — the fix pattern is narrow and has three independent precedents already in this exact codebase (Connector M6.3-1, the AI engine's own tenant-correction convention, Security Engine's M7.3-W3 `secret.put`), so it is Workstream 1, not a redesign.

## 9. Governance Analysis

Confirmed by direct trace, not assumed: the full `context_snapshot`/`ApprovalQueue`/resume chain M7.3 exercised is entirely engine-agnostic — nothing in `KernelDurableApprovalBridge`, `DurableAIApprovalPolicy`, `_on_approval_decided`, or `ApprovalQueue.tsx` references "connector" by name or type; all of it keys off `ToolDefinition.is_mutation` and generic tool-call/task metadata. **No Document-specific approval UX is necessary.** Setting `is_mutation=True` on the `operation.execute` tool is sufficient — the exact same statement M7.3's own report made for Connector, now independently re-confirmed true for a second, unrelated target engine, which is itself useful evidence that this mechanism generalizes correctly rather than having been accidentally Connector-specific.

## 10. Product Use Case

Evaluated against the five candidate use cases:

- **A. Find/read a document** — low product value alone; a document search/read tool without any generation capability is a thin wrapper with limited conversational value.
- **B. Generate a document from a template** — **highest first-product-value candidate**: `execute_profile` already exists, already writes tenant-scoped output, already has a real adapter-pipeline execution path; this is a complete, demonstrable, governed AI capability ("draft an invoice for X") in one tool.
- **C. Modify/update a document** — no capability directly matches "arbitrary update"; the closest primitive is `transition_lifecycle` (state changes, not content edits) — real but narrower, and its more severe tenant gap (§8) makes it a good second tool, not the first.
- **D. Move a document through its lifecycle** — same primitive as C; natural second mutation tool after generation is proven.
- **E. Use document knowledge/context in a conversation** — this is architecturally the *Knowledge Engine's* domain (`IKnowledgeQueryPort`, already wired into AI context composition per the AI engine's own closeout doc), not Document Engine's — conflating the two would combine unrelated features merely because they share a desktop folder (exactly what §11 warns against).

**Recommended flow** (mutation): `user intent ("generate an invoice") → AI proposes operation.execute tool call → approval (existing, unmodified) → execution (existing pipeline, now tenant-safe) → result → conversation response, including the generated document's identifying metadata (not raw bytes — see §13)`.
**Recommended flow** (read): `user intent ("what templates exist") → AI proposes template.list tool call → immediate dispatch (no approval, read-only) → result → conversation response`.

## 11. Proposed Architecture

**Scope boundary — Document Knowledge vs. Document write path**: this proposal is **document write path (generation + lifecycle) only, explicitly excluding Document Knowledge (Knowledge Engine) integration**. Reasoning: Document Knowledge (semantic search/retrieval over document content) is a different engine, already has its own AI-context-composition integration point (`IKnowledgeQueryPort`), and touching it would require its own security/governance analysis this planning pass did not perform — bundling it in would violate the "smallest coherent slice" instruction and the explicit warning against combining unrelated features. The write path (generation via `execute_profile`, state transitions via `transition_lifecycle`) is a self-contained, evaluable slice with existing backend maturity and a direct M7.3-pattern precedent to reuse.

**Target end-state architecture** (consolidating §4/§7/§9 into one concrete picture — nothing below is new infrastructure, every box already exists except the two new `ToolDefinition`s and the W1 fix):

```
AI Studio Chat (existing, unmodified)
    ↓ kortex.ai.agent.orchestrate (existing, unmodified)
AgentOrchestrator (existing, unmodified)
    ↓ LLM proposes a tool call
ToolRegistry — 2 NEW ToolDefinitions: document_list_templates, document_generate
    ↓
AIToolInvoker → KernelToolExecutionPort → CapabilityDispatcher (existing, unmodified, generic)
    ↓
DocumentEngine.list_templates / .execute_profile
    — execute_profile now tenant-safe (W1 fix applied here, and only here for the
      two capabilities this milestone actually exposes as tools)
    ↓
TemplateLibrary / DocumentOperationProfileManager / AdapterPipelineExecutor / AdapterSandbox
    (existing, fully implemented, tenant-scoped at the storage layer already,
    execution-isolated by AdapterSandbox's zero-subprocess/eval/exec/network-I/O guarantee)
    ↓
StorageEngine (existing, unmodified) — tenant-namespaced output object key,
    now backed by a verified tenant_id instead of a caller-supplied one
    ↓
mutation path only: DurableAIApprovalPolicy → DurableApprovalManager → ApprovalQueue.tsx
    → human decision → event-driven resume (existing, unmodified end to end)
    ↓
ToolResult → conversation history (existing, unmodified) — carries identifying
    metadata only (profile, output reference, status), never raw document bytes (T4, §15)
```

Desktop: **no new component in this diagram** for the minimum slice — AI Studio's existing `ChatPanel`/`ToolCallCard` render both tools with zero changes. The optional W3 Operations tab, if greenlit, attaches as a sibling consumer of the same `execute_profile`/`list_profiles`(new)/`transition_lifecycle` capabilities, not a dependency of the AI path.

## 13. Frontend Plan

**Strong preference confirmed applicable**: AI Studio can consume `document_generate`/`document_list_templates` through tool calls with **zero AI Studio code changes** (identical to M7.3 — `ChatPanel`/`ToolCallCard` already render generic tool calls and approval cards). This is the primary interaction surface for the recommended minimum slice.

**Document app changes**: minimal, optional for the smallest coherent slice — the existing read-only `document-knowledge` app needs no changes to support the AI-tool path (the AI path is entirely independent of the desktop UI, exactly as Connector's AI-tool path didn't require `ConnectorsApp` changes — only the *separate* Connections-management UI did). A desktop UI change becomes necessary only if the product goal includes **letting a human directly trigger generation without going through chat** — a real, plausible want, but a distinct, addable-later UI surface, not a prerequisite for the AI-tool slice itself. If included: extend `DocumentKnowledgeApp` with an "Operations" tab (mirroring `ConnectionsTab`'s pattern) rather than a new app/route.

**Minimum UI for the conversation result**: a generated document's *result card* needs to show identifying metadata (profile name, output location/reference, execution status) — **never raw document bytes inline in chat** (mirrors the "never return secrets in a tool schema" principle from M7.3, generalized: don't return large/sensitive binary payloads into conversation history either). This requires no new design-system primitive; `ToolCallCard`'s existing generic rendering already handles arbitrary JSON-shaped tool output.

## 22. Open Questions

1. **Should M7.4 include the optional desktop Operations UI (W3), or ship as an AI-Studio-only capability first?** Why it matters: W3 adds real scope (new tab, new hooks, new tests) that isn't required for the core AI-tool product value. Recommended answer: ship AI-Studio-only first (W1+W2), treat W3 as an immediate, cheap fast-follow once the pattern is proven — mirrors how M7.3 shipped both AI tools and the Connections tab together, but Document Engine's read-only desktop app is already further along than Connectors' was, so less urgency to bundle. Consequence of including W3 now: larger single milestone, more to certify together; consequence of deferring: two smaller, faster-to-review milestones.
2. **Is the discovered tenant-isolation issue (§8) in scope for M7.4, given it also affects capabilities never exposed to AI (`preview.generate`, `intelligence.analyze`, `recommendation.get`)?** Why it matters: fixing only the two AI-exposed capabilities leaves a documented, known vulnerability un-remediated in three others. Recommended answer: sweep all affected capabilities in W1 (cheap, precedented, avoids shipping a "partially fixed" security finding) — see §17.5 file map's SHOULD-CHANGE distinction. Consequence of narrowing to only the two AI-touches: smaller diff, but a security finding this report documents remains open with no tracked follow-up unless one is explicitly created.
3. **Should a generated document be immediately persisted, or returned as a governed, not-yet-committed artifact pending approval?** Why it matters: `execute_profile` already persists output as part of its normal operation (§9's flow assumes approval happens *before* `execute_profile` is ever called, via the existing pause-before-dispatch mechanism — so this is actually already answered by the existing architecture, not a new design question). Recommended answer: no change needed — approval already gates *whether the call happens at all*, not a post-hoc undo of a persisted write, exactly matching how Connector's mutating action already works. Consequence of misunderstanding this: none, if the existing pattern is followed correctly; flagged only so a future implementer doesn't invent an unnecessary "draft vs. committed" state machine that doesn't match how the rest of the platform's governance already works.
4. **Is Document Engine actually the product owner's intended next priority, given Marketplace and the pilot business module are also named in the roadmap note with no stated ordering?** Why it matters: this report's recommendation is risk/reuse/dependency-order-based, not a stated business-priority decision. Recommended answer: proceed with Document Engine per §5's scoring. Consequence of choosing Marketplace or the pilot module instead: a substantially larger, higher-uncertainty milestone with less existing infrastructure to build on — not wrong, just a different risk/value tradeoff than this report was asked to optimize for.
