### 5. Sidecar: exactly how backend startup now works

1. `lib.rs`'s `.setup()` calls `backend_process::spawn_and_monitor(app_handle)`.
2. `resolve_backend_sidecar_config` checks `KORTEX_BACKEND_COMMAND` first (future frozen-binary seam); otherwise resolves `backend/` via `env!("CARGO_MANIFEST_DIR")/../../backend` (canonicalized — fails gracefully if absent, e.g. a distributed build with no source tree), resolves a Python interpreter (`KORTEX_PYTHON_EXECUTABLE` override → a project-local `.venv` → bare `python` on `PATH`), and builds `python -m uvicorn kortex.api.main:app --host 127.0.0.1 --port 8000` with `PYTHONPATH=<backend>/src` and the two persistent keys as env vars.
3. `secure_keys::load_or_generate_backend_keys` loads each key from the OS keyring (service `kortex-desktop`, distinct entries from the session-token entry) or generates+persists a fresh 32-byte CSPRNG value (`getrandom`) on first use, `0x`-hex-encoded — the exact format `kernel_bootstrap.py::_resolve_key` already decodes.
4. `SidecarManager::spawn()` (extended with `working_directory`/`env_vars`, previously absent) launches the process; on success, app state becomes `SidecarSupervision::Active`; on any failure (resolution or spawn), it stays `Disabled` and the existing backend-unreachable UX takes over — never a panic, never a silent hang.
5. A background `tokio::spawn`ed monitor polls liveness every second and applies the pre-existing `RestartPolicy` (max 3 attempts, 100/200/400ms backoff) on an unexpected exit, stopping permanently once the shutdown-intent flag is set or restarts are exhausted.
6. `CloseRequested`/`ExitRequested` set that flag, then call the existing `SidecarSupervision::shutdown()` (graceful stdin-close, 30s grace period, forced kill fallback) — unchanged.

### 6. First-Run Bootstrap: detection, creation, closure, concurrency

- **Detection**: `AuthenticationManager.is_bootstrap_required()` — `SELECT COUNT(*) FROM security_principals`; zero means bootstrappable. Surfaced via `GET /health`'s new `bootstrap_required` field — deliberately not a new capability (no need to widen the bootstrap-exemption allowlist for a read that already has a more appropriate, already-unauthenticated home).
- **Creation**: `bootstrap_first_admin(tenant_id, principal_id, password, roles=["admin"], permissions=<dynamically gathered>)`, one `execute_in_transaction` call performing three inserts: a fixed sentinel `PrincipalRecord` (`tenant_id="__system__"`, `principal_id="__bootstrap_lock__"`, `enabled=False`, `credential_hash=None` — never authenticatable even if guessed), the real admin `PrincipalRecord`, and one `RolePermissionRecord` per granted permission.
- **Closure**: the transaction's own leading `SELECT COUNT(*)` check rejects (`BootstrapClosedError`) the instant any principal exists — true for every call after the first successful one, including the sentinel itself.
- **Concurrency**: two callers can both pass the count check before either commits; both then attempt to insert the *identical* sentinel key, and `PrincipalRecord`'s pre-existing `UniqueConstraint(tenant_id, principal_id, principal_type)` (unmodified, from M3) lets the database reject the loser's entire transaction — sentinel, admin principal, and RBAC grants together, not just the sentinel. There is no window where a second admin is created and no window where a caller observes a sentinel-only, half-bootstrapped system.
- Proven directly by `test_concurrent_bootstrap_attempts_only_one_wins` (`asyncio.gather` of two genuinely concurrent calls) and by the cold-start e2e test's explicit second-attempt-is-rejected assertion.

### 8. Security Verification

- **Bootstrap closure**: proven fail-closed sequentially and under real concurrency (§6, §7).
- **Tenant isolation**: the bootstrap capability takes no caller-supplied `resource_tenant_id`/context — the created principal's `tenant_id` is exactly the submitted value, nothing cross-tenant is read or written. The sentinel lives under a reserved `__system__` tenant_id that can never collide with a real tenant and can never authenticate (`enabled=False`, `credential_hash=None` — proven by `test_bootstrap_lock_sentinel_can_never_authenticate`).
- **RBAC**: the new capability is registered with `requires_authentication=False` (the only two-member allowlist this exists on now, both enforced at the same single choke point as before) and no `required_permissions` (moot — unauthenticated capabilities skip the RBAC step entirely, matching `auth.authenticate`'s own precedent exactly). The RBAC grant *made by* the capability is fully dynamic, gathered from the live capability registry, never hand-maintained, so it cannot silently drift stale as new engines register new capabilities.
- **Secret handling**: the submitted password is never logged, never included in any exception message or audit context — confirmed the literal parameter name `password` is already in the pre-existing `SENSITIVE_KEY_NAMES` redaction set the generic dispatch audit path (`sanitize_for_persistence`) already applies to every capability's parameters, so this required zero new redaction logic. Rust's `eprintln!` status lines never print key material, only high-level status strings and non-secret paths/errors.
- **Persistent keys**: never in source, never in git, never sent to the frontend/webview — generated and read entirely within the Rust process and injected directly into the spawned backend's environment; the webview has no code path that could ever observe them.
- **Process lifecycle**: the shutdown-intent flag (set before `shutdown()` is called) is what lets the crash-monitor distinguish an intentional exit from a crash — without it, every clean shutdown would have been misread as a crash needing a restart.
- **Startup failure behavior**: bounded, never infinite, never busy-looping (real timer delays); a clear terminal UI state with a manual-retry action; sidecar resolution/spawn failure degrades to the pre-existing unreachable-backend UX rather than crashing the app.

### 9. Notable Adaptation (Rule 1) — not a stop condition

`RegistryEngine.register_capability` enforced a hard, single-value invariant (`name != _BOOTSTRAP_EXEMPT_CAPABILITY` raises) reserving the authentication-bypass carve-out for exactly `kortex.security.auth.authenticate`. A naive new unauthenticated bootstrap capability would have been rejected at boot. Widened to a fixed two-member allowlist (`_BOOTSTRAP_EXEMPT_CAPABILITIES`) rather than treated as a stop condition, because: (a) the underlying principle the invariant protects — "reachable before any session token can exist" — applies identically to the new capability by construction (there is no session token on a fresh install, by definition); (b) it does not weaken any existing capability's protection, only recognizes a second, equally-justified member; (c) closing exactly this gap is what M7.1 was chartered to do. Documented here and in both files' own comments rather than made silently.
