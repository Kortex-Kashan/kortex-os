# KORTEX OS — M7.4 Implementation Report
## Document Engine ↔ AI Studio Integration

---

### 1. Executive Summary

**COMPLETE.** AI Studio agents can now safely list document templates and generate documents through the existing, production Document Engine — a second, engine-agnostic proof (after M7.3's Connector Engine) that the AI tool-invocation chain built in M7.2/M7.3 generalizes without modification. No new engine, sandbox, approval mechanism, or content-security layer was built. This milestone is additive wiring, plus one security gate that had to close *before* any AI surface could be exposed:

1. **Tenant-isolation security gate (W1, must-fix-first)**: three Document Engine handlers reachable from Kernel dispatch (`execute_profile`, `transition_lifecycle`, `bind_template`) derived their tenant scope from caller-supplied data (a `BindingContext`/`tenant_id` field embedded in the request payload) instead of the Kernel-verified `principal.tenant_id` — the exact class of gap M6.3-1 and M7.3's own planning found and fixed in the Connector Engine. Left open, any of these three capabilities would have let a tenant-B AI agent operate against tenant A's documents by simply naming tenant A's ids. Fixed before any tool registration, per the master prompt's explicit ordering requirement.
2. **Missing read capability (W2)**: `DocumentProfileManager.list_profiles` existed with full tenant-scoped logic but was never exposed as a Kernel capability — nothing let a tenant, human or AI, discover which operation profiles were available to generate.
3. **Zero AI tools for the Document Engine** existed anywhere before this milestone — `document_list_templates` (read) and `document_generate` (mutation, approval-gated) are new.

One independently-discovered, genuinely pre-existing bug was fixed as a direct, necessary consequence of exercising `transition_lifecycle` through real Kernel dispatch for the first time in this repository's history: the platform-wide dict→Pydantic coercion added in M7.2 (`core/dispatch.py::_coerce_model_parameters`) never resolved `Enum`-typed parameters, only `BaseModel`-typed ones, so a real dispatch call passed `target_state` as a plain string and crashed deep in the persistence layer. Fixed narrowly inside `transition_lifecycle` itself (not a platform-wide dispatch change — out of scope and unnecessary, since no other Enum-typed capability parameter is known to exist).

One AST-enforced architecture-compliance test broke as a direct, legitimate consequence of the W1 fix's new `kortex.engines.security` import and was fixed with a narrowly-scoped allowlist extension, modeled on the existing storage-submodule carve-out.

Two capabilities in scope for a shallow tenant-isolation fix (`analyze_document_intelligence`'s downstream provider call, and by extension `recommendation.get`/`preview.generate`) were investigated and deliberately **not** fixed: the underlying `IDocumentIntelligenceProvider.analyze_document` protocol has no `tenant_id` parameter at all, so closing this gap requires a protocol-level change out of scope for this milestone. Documented as a known limitation (§16), not silently worked around.

No desktop change was required or made — AI Studio's existing generic tool-call rendering and Workflow Approval Queue already cover the new Document tools with zero UI-side code, exactly as they did for M7.3's Connector tools.

### 6. Architecture

The final, real dispatch path — no component below the Kernel boundary is new, and this is the identical chain M7.3 proved for the Connector Engine, now proven a second time against an entirely different engine:

```
AI Studio Chat
    ↓ kortex.ai.agent.orchestrate (existing, M7.2)
AgentOrchestrator (existing)
    ↓ LLM proposes a tool call
AIToolInvoker (existing) → ToolRegistry.get_tool() (existing type, newly populated for Document)
    ↓ validates arguments against parameters_schema (existing)
KernelToolExecutionPort.execute_tool (existing)
    ↓ kernel_bridge.invoke_capability(...)
CapabilityDispatcher.dispatch (existing) — authenticate → authorize (RBAC) → derive tenant
    → invoke handler(principal=...)
DocumentEngine.list_profiles / .execute_profile (M7.4-W1/W2 — principal.tenant_id now authoritative)
    ↓
DocumentOperationProfileManager / AdapterSandbox / persistence (existing, untouched)
```

The only things that did not exist before this milestone: `principal`-derived tenant binding on three existing handlers (W1), one new capability wrapping an already-existing manager method (W2), two `ToolDefinition`s registered into `ToolRegistry` (W3), and one narrow `Enum`-coercion fix plus one architecture-compliance-test allowlist extension, both discovered as direct consequences of exercising real dispatch for the first time.

### 7. Security Findings and Fixes (W1)

| Handler | Capability | Gap found | Fix |
|---|---|---|---|
| `execute_profile` | `kortex.document.operation.execute` | `binding_context.tenant_id`, if present, was caller-supplied and used as-is | `principal is not None` → `binding_context = binding_context.model_copy(update={"tenant_id": principal.tenant_id})` before the profile manager is invoked |
| `transition_lifecycle` | `kortex.document.lifecycle.transition` | `tenant_id` was not derived from `principal` at all — the method had no tenant awareness on the dispatch path | `tenant_id = principal.tenant_id if principal is not None else "default"`, threaded into both the lineage lookup and `_lifecycle_manager.transition_state` |
| `bind_template` | `kortex.document.template.bind` | Same pattern as `execute_profile` — caller-supplied `context.tenant_id` used as-is | `principal is not None` → `context = context.model_copy(update={"tenant_id": principal.tenant_id})` before `get_template` |

All three follow the identical `principal`-authoritative pattern established in M6.3-1 for the Connector Engine and reused unchanged in M7.3: the Kernel dispatcher injects the verified `principal` into any handler parameter literally named `principal`; every handler above now uses it to override, not merely validate, any caller-supplied tenant identifier.

**Adversarially tested** (`test_document_tenant_isolation_dispatch.py`, §13): a tenant-B principal invoking `execute_profile` against a profile that only exists under tenant A gets `DocumentProfileNotFoundError` — never tenant A's real result. A tenant-B principal invoking `transition_lifecycle` against a tenant-A document id gets `DocumentLifecycleError` — never a successful state change on tenant A's document. `list_profiles` returns only the caller's own tenant's profiles, proven by seeding both tenants and asserting the returned set.

**Deliberately not fixed, and why (§16 has the full accounting)**: `analyze_document_intelligence`, `recommendation.get`, `preview.generate` all ultimately call into `IDocumentIntelligenceProvider`-family protocols whose method signatures (`analyze_document(document_id, version_id, ontology=None)`, etc.) carry no `tenant_id` parameter whatsoever. Adding tenant derivation at the `DocumentEngine` facade level would silently no-op — the tenant value would have nowhere to go. A real fix requires extending the protocol itself, which is a deeper, multi-file change this milestone's own scope guardrails ("do not blindly mirror... only expose operations justified by existing architecture and M7.4 requirements") correctly exclude: none of the three is part of the minimum AI tool surface (§8), and none is reachable by the two new tools.

### 8. AI Tool Architecture (W3)

Two `ToolDefinition`s (`kernel_bootstrap.register_document_ai_tools()`, called once at boot against `ai_engine.tool_registry`, immediately after `register_connector_ai_tools`):

| Tool | `canonical_capability` | `is_mutation` | Gate |
|---|---|---|---|
| `document_list_templates` | `kortex.document.template.list` | `False` | none — dispatches immediately |
| `document_generate` | `kortex.document.operation.execute` | `True` | `DurableAIApprovalPolicy` (existing, unmodified) |

**Schema shape**: `document_generate`'s `parameters_schema` nests `request_id`/`profile_id`/`binding_context` under a top-level `request` object matching `DocumentEngine.execute_profile(self, profile_id, request, principal=None)`'s real two-parameter signature — the Kernel dispatcher splats capability parameters as `handler(**parameters)`, so `profile_id` and `request` are both top-level tool arguments, with `request` itself carrying the nested `OperationRequest` shape. This mirrors M7.3's own corrected schema-shape lesson (§8 of the M7.3 report): the schema was built from the real handler signature, not assumed uniform with the Connector Engine's differently-shaped `execute_action(self, request, principal=None)`.

`document_list_templates` takes no parameters — `DocumentEngine.list_templates()` (the existing, already-tenant-scoped capability this tool wraps) needs none beyond the principal the Kernel already injects.

### 9. Capability Exposure (W2)

One new capability: `kortex.document.profile.list` → `DocumentEngine.list_profiles`, permission `document:read` (reused, already existed — no new permission string was needed, unlike M7.3's `security:secret:write`, because `document:read` already gates every other read-only Document capability and `profile.list` is equivalently sensitive). Wraps `DocumentOperationProfileManager.list_profiles(tenant_id=...)`, which already had full tenant-scoped logic — this was pure exposure, no new business logic. Registered in `DocumentDiagnostics.capabilities()` as the 10th entry (was 9).

Deliberately not added: `profile.register`/`.delete`. No AI tool or E2E acceptance scenario in the planning report's scope needs a way to create or remove an operation profile via AI — profiles are an administrative/deployment concern, not a per-conversation one. Mirrors M7.3's identical reasoning for not adding `secret.delete` or `profile.update` beyond the minimum justified surface.

### 10. Approval Flow (W4)

Zero new code. `document_generate`'s `is_mutation=True` is the only signal `DurableAIApprovalPolicy` needs — the exact same policy, the exact same `DurableApprovalManager` queue, and the exact same `ApprovalQueue.tsx` UI that governs every other AI-originated mutation (Workflow Engine's external executions in the M5.1–M6.4 track, Connector Engine's `connector_send_action` in M7.3, and now Document Engine's `document_generate`). Approve → `_on_approval_decided`'s existing APPROVED branch → `AgentOrchestrator.resume_task` → real `DocumentEngine.execute_profile` dispatch. Reject → `cancel_task`, zero dispatch.

**Idempotency**: proven identically to M7.3 (`test_ai_document_tool_invocation.py::test_duplicate_approval_decided_event_does_not_dispatch_the_document_generation_twice` — captures the real event a real approval decision publishes and re-delivers it directly to `AIOrchestrationEngine._on_approval_decided`, proving no second dispatch). This is the same pre-existing, engine-agnostic `PAUSED_FOR_APPROVAL → RESUMING` CAS guard M7.3 documented — no Document-specific idempotency code was needed or written.

### 11. Content Security and Sandbox Verification (W5/W6)

**Sandbox**: `AdapterSandbox` (zero subprocess, zero eval/exec, zero network I/O, capability allowlisting, timeout enforcement, guaranteed workspace cleanup) was not modified in any way. The AI path reaches the identical `AdapterSandbox` instance through the identical `DocumentEngine.execute_profile` → `DocumentOperationProfileManager` → adapter-pipeline chain that every other caller already uses — only the caller (`AIToolInvoker` instead of a direct API/desktop call) differs, exactly as M7.3 found for the Connector Engine's `HttpRestConnectorDriver`.

**Content-security claim, corrected during implementation**: an earlier draft of this milestone's tool docstring overstated a "new" truncation guarantee for document output entering conversation history. The actual, accurate claim: `OperationResult.output_bytes` (potentially large — a generated document) flows through `ToolResult.to_context_entry()`'s existing, generic `MAX_TOOL_OUTPUT_CHARS=50_000`/`max_tool_result_bytes=65_536` truncation and `scrub_secrets_from_text` scrubbing (both pre-existing since before M7.3, engine-agnostic) before ever entering agent step history — no new truncation code was written for Document specifically, because the generic backstop already applies to any tool's output, byte-identical to how it already bounds Connector Engine responses. Corrected in the tool's docstring and proven, not merely asserted, by `test_large_document_output_is_bounded_before_entering_conversation_history` (§13): a 200,000-byte `output_bytes` payload is confirmed truncated and marked `TRUNCATED` after passing through the real, unmodified `to_context_entry()` path.

### 14. Regressions Found and Fixed

Two real regressions surfaced as direct, necessary consequences of this milestone's own changes — both root-caused before being fixed, neither dismissed as "pre-existing" without proof:

1. **`test_architecture_compliance_assertions` failure**: Document Engine's AST-enforced import-boundary test rejected the new `from kortex.engines.security.models import SecurityPrincipal` import (`"security"` is not in `DocumentEngine().dependencies() == ["storage"]`, and no submodule-level carve-out existed for it, unlike storage's pre-existing `_STORAGE_ABSTRACTION_SUBMODULES = {"interfaces", "models"}`). Verified Connector and Workflow Engines both already import `SecurityPrincipal` the identical way without declaring `"security"` as a dependency — this is a Document-Engine-specific stricter rule, not a violation of precedent elsewhere. Fixed with a narrowly-scoped `_ALWAYS_ALLOWED_UNDECLARED_ENGINE_SUBMODULES = {"security": {"models"}}` allowlist, modeled directly on the storage carve-out's own reasoning (pure DTOs are an architecturally sound exception; concrete engine internals are not). Verified passing in isolation.

2. **`transition_lifecycle` `Enum` coercion crash** (a genuinely independent, pre-existing bug, not a regression from this milestone's own edits, but discovered only because this milestone was the first code in the repository's history to exercise `transition_lifecycle` through real Kernel dispatch instead of a direct Python call with a real enum instance): M7.2's `_coerce_model_parameters` (`core/dispatch.py`) only resolves `BaseModel`-typed parameters, never `Enum`-typed ones, so `target_state` arrived as a plain string and crashed in `persistence.py`'s `record.lifecycle_state = target_state.value`. Verified via repo-wide grep that no existing test had ever exercised this method through real dispatch. Fixed narrowly, inside `transition_lifecycle` itself: `if isinstance(target_state, str): target_state = DocumentLifecycleState(target_state)`. Not fixed at the platform-wide dispatch level — no second Enum-typed capability parameter is known to exist in the codebase today, so a generic dispatch-layer fix would be speculative, unjustified scope expansion.

### 16. Known Limitations

1. `analyze_document_intelligence`, `recommendation.get`, `preview.generate` still derive no tenant identity from `principal` — the underlying `IDocumentIntelligenceProvider`-family protocols have no `tenant_id` parameter at all, so a facade-level fix would silently no-op. None of the three is part of the AI tool surface added this milestone (§7). A real fix requires a protocol signature change, out of scope here.
2. `OperationRequest.binding_context: BindingContext = Field(default_factory=BindingContext)` is reachable-but-always-broken when omitted: `BindingContext.context_id: str` has no default, so the bare factory call raises a Pydantic validation error the instant it's invoked. Discovered while writing this milestone's own tests (worked around by always explicitly supplying `binding_context`); not a regression from this milestone, and fixing the model's own default-factory design is unrelated Document Engine cleanup outside this milestone's scope.
3. `kortex.security.secret.get` and `kortex.ai.agent.cancel`/`.status`/`.list` tenant-derivation gaps, both flagged and left open in M7.2/M7.3's own reports, remain untouched — genuinely out of scope for a Document Engine milestone.
4. No `document.profile.register`/`.delete` capability — an operation profile is provisioned administratively today; nothing in this milestone's AI-tool or acceptance scope needs AI-driven profile lifecycle management (§9).
