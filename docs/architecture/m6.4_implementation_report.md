### 4. Problems Found

1. **Real bug, not environmental (the actual point of this pass).** The prior session's full-suite run hung twice and was misdiagnosed as an environmental stall. Instrumenting with `pytest-timeout` (installed locally for diagnosis only, not added to the repo) produced an actual traceback: the hang was inside `pytest_asyncio`'s own event-loop teardown, blocked forever on `asyncio.gather(*to_cancel, ...)` waiting for a task that had been `.cancel()`-requested but never actually awaited to completion.
2. **AI-originated approval tickets could never expire at all**, independent of anything M6.4-1 through M6.4-5 built. `DurableAIApprovalPolicy.requires_approval` never forwarded any `timeout_seconds` value to the approval bridge — confirmed by grep (zero occurrences) and by tracing the full call chain down to the `kortex.workflow.approval.create` capability, which already fully supports the parameter.

### 5. Problems Fixed

**Fix 1 — `WorkflowEngine._stop_approval_sweep_loop` (commit `cb77aa1`).** The original M6.4-2 code called `task.cancel()` and returned immediately without awaiting the task. Because `approval_sweep_enabled` defaults to `True`, this task now starts on *every* production-shaped Kernel boot (`kernel_bootstrap.build_and_boot_kernel()` constructs `WorkflowEngine()` with no override) — not just the handful of tests written to exercise it directly. A leak here compounds across a real suite of ~2300 tests, each doing its own boot/shutdown cycle. Rewritten to mirror the exact cancel-then-await pattern already established in the same method for `self._running_tasks`, with a bounded 5s `wait_for` as a last-resort safety net.

Confirmed as the actual root cause, not a guess: the exact 34-test slice that reliably preceded the hang point passed cleanly in 76s after the fix (previously never completing); the full suite then completed twice in a row, ~16 minutes each, with zero hangs.

**Fix 2 — AI approval timeout wiring (commit `57bef0f`).** Classified as a genuine M6.4 blocker, not a deferrable gap (see §6 reasoning below), and fixed: `IDurableApprovalBridge`/`KernelDurableApprovalBridge.create_request` now forward `timeout_seconds`; `DurableAIApprovalPolicy` gained an `approval_timeout_seconds` constructor parameter defaulting to 86400 (reusing the value, not the wiring, of the otherwise-dead `WorkflowSettings.approval_timeout_seconds`). Both production call sites (`bootstrap.py`, `engine.py`) needed zero changes — the default flows through automatically.

**Fix 3 — direct regression test for Fix 1.** `test_approval_sweep_loop_stop_actually_awaits_task_completion` proves `_stop_approval_sweep_loop()` doesn't return until the task is unconditionally `.done()`.

### 17. Remaining Risks

- `approval_sweep_interval_seconds` defaults to 30s — up to ~30s expiry latency in production; acceptable given realistic approval-timeout scales of minutes to hours.
- `DurableWorkflowScheduler.stop_background_loop()` shares Fix 1's bug class but isn't exercised by default (§6) — worth a follow-up fix whenever that scheduler is next touched.
- The `tzdata` package gap (§16) will keep failing that one test in this specific environment until installed; not a KORTEX code issue, not fixed here (out of M6.4's scope, and a one-line environment fix — `pip install tzdata` — for whoever owns this machine's setup, not a repo change).

### 19. M6.5 Recommendation

**PROCEED WITH ORIGINAL ROADMAP.**

None of §6's deferred items block whatever comes next. They don't share enough architectural cohesion to justify a dedicated milestone: the AI-orchestrator race and boot-reconciliation gap are AI-module-internal correctness/completeness work; the AI audit-trail gap is an observability initiative; the outbox-drain gap is a *different*, broader event-delivery-reliability concern that touches every engine using the outbox, not just approvals, and deserves its own properly-scoped effort whenever the team prioritizes it — bundling these together under a new "M6.5" would be exactly the kind of cleanup-bucket milestone the master prompt cautioned against, not a milestone with its own coherent value proposition. The core objective — a hardened, adversarially-tested, production-reachable, fully-certified approval lifecycle — is now actually achieved, not just claimed. Recommend tracking the five deferred items (§6) as independent, small follow-up tickets, picked up opportunistically or when AI orchestration work is next prioritized, rather than gating the roadmap on a new milestone.
