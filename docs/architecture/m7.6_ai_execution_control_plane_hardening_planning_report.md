## 1. Executive Summary

The evidence does **not** point to another "connect engine X to AI" milestone. M7.3, M7.4, and M7.5 each proved the same integration pattern works; a sixth research pass (this one) specifically looked for whether that pattern has started accumulating control-plane debt rather than assuming it has, and found a concrete, verified answer: **yes, in one specific, well-scoped place.**

`AIOrchestrationEngine._on_approval_decided` — the *only* code path that resumes an AI agent task after a human approves a mutating tool call, and therefore the path every mutating AI tool built so far (`connector_send_action` M7.3, `document_generate` M7.4) actually depends on in production — calls `AgentOrchestrator.resume_task(...)` directly, with **no `TenantConcurrencyThrottler.acquire_agent_slot()` wrapping at all**. Both of the *synchronous* entry points into the same orchestrator (`orchestrate_agent`, `resume_agent`) correctly wrap their calls in `async with self._throttler.acquire_agent_slot(task.tenant_id):`; the asynchronous, event-driven resume path does not. This was verified directly by reading `engine.py` (§8), not merely reported by a research agent. It is not a tenant-isolation/data-leak defect — tenant lookup fails closed and task state is server-stored, not payload-trusted — but it is a real concurrency-control gap: the per-tenant cap that exists specifically to bound how many agent workflows can run at once for one tenant does not apply on the one path every approved mutation actually resumes through.

Three smaller, concrete, evidence-based gaps were found alongside it, all in the same AI control-plane surface: (a) the boot-time AI-tool-registration idempotency test that exists for the Connector tools (`test_kernel_bootstrap.py`) was never mirrored for the Document or Knowledge tools, a gap M7.5's own report flagged and left open; (b) `AITelemetryEmitter.emit_tool_invoked` (the success-path telemetry event) does not record `execution_time_ms`, even though `ToolResult.execution_time_ms` is already computed by `AIToolInvoker.invoke_tool` before the event fires — only the failure/denial paths currently record latency; (c) the AI Studio desktop chat surface deliberately discards `AgentExecutionResult.steps`/`total_token_usage` when building its transcript type, and `AiGovernanceTab.tsx`'s audit-log row already receives `toolCallsRequested`/`approvalRequestId` on `AIDecisionAuditRecord` but never renders them — real operational data the backend already computes, invisible in the one UI built to show governance activity.

Four candidates investigated and ruled out with concrete evidence, not assumption: AI tool consolidation/catalog architecture (5 tools across 3 engines remains coherent — consistent naming, uniform error handling, one deliberate and well-documented schema divergence, no capability collisions beyond the one already-established `const`-trick); AI cost/token/latency control (already substantially bounded — `MAX_BATCH_SIZE=10`, `max_steps` clamped 1–30, loop detection at 3 repeats, windowed conversation history at a 200-turn ceiling and a 10-step/2000-char step-history window — no evidence of unbounded growth); Marketplace integration (unchanged since M7.5's own investigation — a one-capability, in-memory, read-only stub with no write path, confirmed via `git diff` that zero commits since then touched it); business-module/RecipeEngine integration (unchanged since M7.5 — zero real implementation, RecipeEngine unwired at boot).

**Recommended M7.6: AI Execution Control Plane Hardening** — close the throttle-parity gap on the approval-resume path (the primary, security/reliability-relevant fix), backfill the two missing AI-tool-registration idempotency tests, and complete the tool-invocation telemetry's latency field on success. Desktop observability work (surfacing `steps`/token usage/`toolCallsRequested` into the chat transcript and governance audit log) is a real, well-evidenced, *separate* concern — recommended explicitly as the next milestone after this one (a likely M7.7), not folded in here, to keep M7.6 narrow and independently reviewable.

## 8. Security / Tenant-Isolation Audit

**New finding, verified directly (not merely agent-reported)** — `backend/src/kortex/engines/ai/engine.py`:

```python
# Lines 984, 1035 — the two SYNCHRONOUS entry points:
async with self._throttler.acquire_agent_slot(task.tenant_id):
    result = await self._agent_orchestrator.run_task(...)   # orchestrate_agent
    # / resume_task(...)                                     # resume_agent

# Line 1501-1505 — the ASYNCHRONOUS, event-driven resume path:
resumed_result = await self._agent_orchestrator.resume_task(
    task=record.task,
    resume_token=record.resume_token,
    approved_tool_calls=record.pending_tool_calls,
)
# ^ no throttler acquisition anywhere in _on_approval_decided
```

This is the *only* path an approved mutating AI tool call (`connector_send_action`, `document_generate`, and any future mutating tool) actually resumes through in production — a human approval decision always arrives asynchronously via the durable `workflow.approval.decided` event, never through the synchronous `resume_agent` API. Every mutation-capable AI tool built across M7.3–M7.5 therefore depends on a resume path that does not enforce the per-tenant concurrent-agent-workflow cap the rest of the system relies on.

**What this is not**: not a cross-tenant data leak (tenant lookup via `get_task(task_id, tenant_id)` fails closed on mismatch; the resumed `task` object comes from the durably stored, originally-validated record, never from the event payload); not a replay/idempotency defect (the CAS in `claim_task_for_resumption` still protects against duplicate dispatch, verified unchanged from M7.3–M7.5's own proofs); not currently exploitable for privilege escalation (RBAC/authorization still runs per-tool-call inside `CapabilityDispatcher`).

**What this is**: a concurrency-control gap. A tenant with many pending approvals (or an approval workflow that batches decisions) can cause more concurrent agent-resume executions than `TenantConcurrencyThrottler`'s `max_concurrent_agents` (default 5) is meant to allow — undermining the resource-exhaustion protection that control exists for, specifically on the one path every mutating AI tool actually uses.

**Cross-engine sweep, reused from M7.5** (unchanged, re-verified via `git diff` showing no relevant commits since): Storage/Registry/Recipe/Marketplace have zero tenant-scoped capabilities. Workflow Engine capabilities were audited clean in M7.5 beyond two already-known, unrelated gaps. No new cross-engine tenant-isolation gap was found this session — the one finding is control-plane-specific, not engine-capability-specific.

## 10. Cost / Token / Latency Audit

Bounded by several independent, already-existing mechanisms: `AgentTask.max_steps` clamped to [1, 30] (default 10); `timeout_seconds` clamped to [1.0, 600.0] (default 60); `AIToolInvoker.invoke_all` hard-capped at `MAX_BATCH_SIZE = 10` tool calls per step; loop detection trips after 3 consecutive identical tool-call-batch hashes; conversation history capped at `_MAX_HISTORY_TURNS_CEILING = 200`; per-step context built from only the last `max_step_history_window` (default 10) steps, each tool result truncated to `max_step_result_chars` (default 2000). `TokenUsage` is actively aggregated per task (`cumulative_tokens`), not merely scaffolded. No evidence of unbounded context growth, runaway tool-call loops, or unmetered token consumption. Per-tool-call cost/token attribution does not exist (only per-LLM-generation), and retry/fallback events are logged and telemetry-counted but not persisted as structured, queryable records — both real gaps, but neither is urgent enough on its own to drive a milestone given the stronger, more concrete finding in §8.

`ResilientAIProvider`'s retry (3 attempts, exponential backoff + jitter) and `ProviderFallbackChain` are real, wired infrastructure — but exactly one provider (`OllamaProvider`) is registered in production (`kernel_bootstrap.py`), so the fallback chain currently has no second candidate to fail over to. This is a genuine single-point-of-failure for the entire AI control plane, explicitly out of scope for M7.6 (§22) — fixing it means provisioning and wiring a second real provider, a separate, larger initiative with no evidence it's needed yet, not a control-plane code change.

## 14. Recommended M7.6

**M7.6 — AI Execution Control Plane Hardening**

**Objective**: Close the tenant-concurrency-throttle gap on the asynchronous approval-resume path — the one path every mutating AI tool actually depends on — and close two small, directly-related AI-control-plane hygiene gaps discovered in the same investigation.

**Problem statement**: `AIOrchestrationEngine._on_approval_decided` resumes an approved AI agent task without acquiring a `TenantConcurrencyThrottler` agent slot, unlike both synchronous orchestration entry points. The per-tenant concurrent-agent-workflow cap this system relies on to bound resource usage does not apply on the path every approved mutation (Connector's `connector_send_action`, Document's `document_generate`, and any future mutating AI tool) actually resumes through.

**User/product value**: Indirect but real — protects tenant-fair-use and system stability as more mutating AI tools are added in future milestones (the exact pattern M7.3–M7.5 established will likely continue). Prevents a class of resource-exhaustion risk from ever becoming exploitable rather than reacting to it after a fourth or fifth mutating tool makes it more consequential.

**Architectural value**: Closes the one asymmetry between the AI engine's two families of task-resumption entry points, making the control plane's concurrency guarantees actually uniform rather than incidentally bypassed on the busiest path (every approval-gated resume). A natural "harden before extending further" step, consistent with the established M6.3/M7.4-W1/M7.5-W1 precedent of fixing a control/security gap before or alongside further engine integration — except this time the gap is in the shared control plane itself, not a per-engine capability handler.

## 19. Testing Strategy

1. **Happy path**: an approval-decided event for a tenant under its concurrency cap resumes normally (unchanged behavior, regression-proven).
2. **Authorization failure**: not applicable to this fix (no new authorization surface).
3. **Concurrency/adversarial path** (the core new test): a tenant at `max_concurrent_agents` capacity, with an additional task pending approval, has that pending approval decided — assert the resume either queues/rejects appropriately (matching whatever `acquire_agent_slot`'s existing behavior is for the synchronous paths — reuse that exact contract, don't invent a new one) rather than silently exceeding the cap.

## 23. Open Questions

1. **What should `acquire_agent_slot` do when the cap is already reached on the approval-resume path specifically** — block until a slot frees, or fail the resume outright (and if so, does the task get cancelled, left paused, or retried)? Why unresolved: the synchronous paths' current behavior (raising `TenantQuotaExceededError`, per `throttling.py`) is appropriate for a live API caller who can retry, but an asynchronous, event-driven resume has no caller to return an error to. Evidence checked: `_on_approval_decided`'s existing broad `except Exception` already logs and swallows errors without re-raising (line 1512-1513) — a `TenantQuotaExceededError` would currently just be logged and the task would stay stuck `PAUSED_FOR_APPROVAL` forever, which is likely wrong. Recommended default: implement the fix so the resume queues (blocks) for a slot rather than raising, since `async with acquire_agent_slot(...)` already supports this if the throttler's own acquire logic is a wait rather than an immediate raise — verify `throttling.py`'s exact semantics at implementation time and pick accordingly, defaulting toward "never leave a task stuck" over "fail fast." What would change the recommendation: if the throttler's `acquire_agent_slot` is confirmed to raise-immediately-never-wait (as its docstring "or raise TenantQuotaExceededError" suggests), the resume path needs explicit handling (e.g., leave the task `PAUSED_FOR_APPROVAL` and let the sweep/retry mechanism reprocess the event later) rather than blindly applying the same context-manager pattern.
