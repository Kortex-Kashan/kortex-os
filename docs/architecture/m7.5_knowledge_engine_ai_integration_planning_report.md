### 1. Executive Summary

The evidence points to one clear next milestone: **close a live, currently-exploitable tenant-isolation gap in the Knowledge Engine, then connect it to AI Studio through the same governed AI-tool pattern proven twice (Connector Engine, M7.3; Document Engine, M7.4).**

This is not a symmetry choice. Five independent lines of investigation (a fresh, current-HEAD Graphify graph; five parallel research agents; and direct source verification of the most consequential claim) converged on the same finding: **all five of the Knowledge Engine's registered Kernel capabilities accept no `principal` parameter at all** — a strictly worse variant of the tenant-isolation gap M6.3 and M7.4 found and fixed elsewhere. Unlike those two milestones, this gap is **not hypothetical or AI-exposure-contingent** — it is already reachable today through the existing, production desktop Knowledge UI (`apps/desktop/src/features/document-knowledge/knowledgeApi.ts`), which passes a client-supplied `tenant_id` straight through to the backend with zero server-side verification. Two of the five capabilities are gated only by ordinary `knowledge:read`/`knowledge:write` permissions — not an admin-only permission — meaning any authenticated user holding a routine permission could read or write another tenant's knowledge graph today by supplying that tenant's id.

Three other candidates were seriously investigated and ruled out with concrete evidence: the Marketplace Engine is a one-capability, in-memory, read-only stub with no write path and nothing for AI to meaningfully act on; the Phase 6 "pilot business module" track has zero backend implementation (an empty `__init__.py` and a README) and its supporting `RecipeEngine` infrastructure, while real, is unwired at production boot and has no concrete content to install — a new-subsystem build, not an integration task, and a materially larger and riskier undertaking than the M7.3/M7.4 pattern; and residual gaps in the already-integrated Connector/Document Engines are minor, already documented, and each independently blocked by a genuine architectural limitation (a missing `tenant_id` parameter on a downstream provider protocol), not new milestone material.

A secondary, real finding — not urgent enough to drive the milestone, but worth addressing opportunistically inside it — is that the AI `ToolRegistry`'s registration mechanism is coherent today (4 tools, consistent naming, one shared truncation/scrubbing pipeline) but is showing early structural debt: no central tool catalog, no category/namespace field, fully copy-pasted per-engine registration functions, and an already-slipped test-coverage asymmetry (the document tools lack the boot-time idempotency unit test the connector tools have). A third engine's tools — this milestone's own `knowledge_search` — is exactly the inflection point at which a lightweight shared registration helper becomes justified by evidence rather than speculation.

Recommended scope is deliberately narrow and read-heavy: fix tenant isolation on all five Knowledge capabilities (justified independently by the live security gap, not merely by AI-exposure needs), register exactly one new AI tool (`knowledge_search`, read-only, no approval required), and leave the desktop untouched. Whether a mutation-class Knowledge AI tool (e.g., AI-triggered source indexing) belongs in this milestone or a later one is flagged as a genuine open product question, not decided here.

### 5. Current Architecture

**KERNEL** — `CapabilityDispatcher.dispatch()` (`core/dispatch.py`): authenticate (`SecurityEngine.authenticate`/`_load_principal`) → authorize (RBAC via `required_permissions`) → derive tenant → invoke handler, injecting the verified `principal` into any handler parameter *literally named* `principal` (confirmed via graph + this session's prior direct code knowledge: `accepts_principal = "principal" in inspect.signature(handler).parameters` — a handler that omits the parameter name is "entirely unaffected," per the dispatcher's own docstring). This single mechanism is what M6.3, M7.4, and now this report's Knowledge finding all turn on.

**AI ENGINE** (`engines/ai/`) — `AgentOrchestrator` (`agent.py`) runs task loops, invoking tools via `ToolRegistry`/`AIToolInvoker` (`tools.py`), which validate against `ToolDefinition.parameters_schema` and dispatch through `KernelToolExecutionPort` → `CapabilityDispatcher`. Exactly **4 `ToolDefinition`s exist in the entire codebase**, all in `kernel_bootstrap.py`: `connector_read_status`/`connector_send_action` (M7.3), `document_list_templates`/`document_generate` (M7.4). `ToolRegistry` is a flat, unindexed `dict[str, ToolDefinition]` with no category/namespace concept. Mutation gating is entirely driven by `ToolDefinition.is_mutation` read by `governance.py`'s `DurableAIApprovalPolicy`. Output entering conversation history passes through one shared, generic pipeline: `MAX_TOOL_OUTPUT_CHARS` (50,000 char) truncation → `scrub_secrets_from_text` → a 64 KiB hard byte ceiling → delimiter neutralization.

**CONNECTOR ENGINE** — mature, production-wired (M7.3), tenant-isolation-hardened (M6.3 + M7.3), 2 AI tools, desktop Connections tab. No new gaps found this session.

**DOCUMENT ENGINE** — mature, production-wired, tenant-isolation-hardened on the 3 AI-relevant handlers (M7.4), 2 AI tools. Known, documented, deliberately-unfixed residual gap: `analyze_document_intelligence`/`recommendation.get`/`preview.generate` can't derive tenant because the underlying `IDocumentIntelligenceProvider` protocol has no `tenant_id` parameter at all — a protocol-level fix, out of proportion for a follow-up milestone on its own.

**SECURITY ENGINE** — `CapabilityDispatcher`'s authentication/authorization backbone; RBAC via `required_permissions`; `SecretStore` encrypted at rest. Two known, already-documented, still-unfixed tenant-derivation gaps, reconfirmed this session: `kortex.security.secret.get` (`engine.py:703`, no `principal` param) and `kortex.ai.agent.cancel`/`.status`/`.list` (`ai/engine.py:1069,1073,1079`, plain `tenant_id: str`, no `principal`). `bootstrap_create_admin` intentionally trusts a raw `tenant_id` pre-authentication — by design (fail-closed after first use), not a defect.

**WORKFLOW ENGINE** — 24 registered capabilities, freshly re-audited this session beyond the already-covered approval/schedule/external-execution track. Result: **clean**. `start_workflow`/`list_instances_durable`/`get_instance_durable`/`resume_workflow`/`cancel_workflow` all correctly apply `principal.tenant_id` precedence. `submit_approval_decision` and `create_schedule` achieve the same safety through a downstream layer (`DurableApprovalManager`/`WorkflowScheduler`) rather than the handler itself — functionally safe today, flagged as a minor consistency/maintainability nit, not a vulnerability.

**KNOWLEDGE ENGINE** (`engines/knowledge/`) — mature and rich (`search`, `index_source`, `load_pack`, `traverse_graph`, `list_nodes`, plus lineage/annotation/pack-manager subsystems), registered at production boot (`kernel_bootstrap.py:224`, after Storage/Security/AI/Document), already has a desktop consumer (`document-knowledge` feature, calling `graph.list`/`graph.traverse`). **All 5 registered Kernel capabilities lack a `principal` parameter entirely** — see §10 for the full finding. Zero AI-tool registration exists for it today.

**MARKETPLACE ENGINE** (`engines/marketplace/`) — registered at production boot, but deliberately minimal: exactly one capability (`kortex.marketplace.listing.list`), an in-memory `MarketplaceCatalogRegistry` with no persistence, and no capability exposing `register_listing`/`clear` — meaning **nothing can populate the catalog in production today**. The engine's own module docstring states this explicitly: "a read-only catalog... every other capability the [full marketplace] spec describes is future, unimplemented work." Desktop has a matching read-only `MarketplaceApp.tsx` ("Installing, purchasing, and publishing are not available yet").

**RECIPE ENGINE** (`engines/recipe/`) — real, generic "declarative recipe → compiled WorkflowDefinition" infrastructure with 10 capabilities, but **not registered anywhere in `kernel_bootstrap.py`** (confirmed: `RecipeEngine()` is instantiated only in test files) and has no concrete recipe/manifest content anywhere in the repository to load through it even if it were wired up.

**BUSINESS MODULES** (Phase 6: Finance/HR/Operations) — `backend/src/kortex/modules/` and `backend/src/kortex/recipes/` each contain only a `README.md` and an empty `__init__.py`. Zero implementation. Every "finance"/"payroll"/"invoice" string match in the repository is an unrelated placeholder/example string in generic Kernel or Workflow-schedule tests, not module code.

**DESKTOP** — six feature apps exist: `ai-studio` (chat, governance tab, tool-call approval cards), `connectors` (Drivers + Connections), `dashboard` (system health), `document-knowledge` (combined Document + Knowledge browse, deliberately read-only), `marketplace` (catalog browse, deliberately read-only), `workflow` (the canonical Approval Queue + schedules + external-execution inspector). The Approval Queue is confirmed the sole decision surface: AI Studio's `ToolCallCard.tsx` explicitly deep-links into it rather than duplicating any decision UI (its own header comment: "this feature must not become a second approval-decision surface"). IPC pattern: a single typed `invokeCapability()` wrapping Tauri's `invoke`, with per-feature `api.ts` wrapping specific capability names and TanStack Query hooks (`useQuery`/`useMutation`) keyed by feature name — any new feature would reuse this unchanged. Every backend business-facing engine already has a desktop surface except Security (no admin/secrets-management UI — looks like a deliberate deferral, not an oversight) and Storage (correctly infrastructure-only).

### 7. Recommended Milestone

**M7.5 — Knowledge Engine ↔ AI Studio Integration**

**Objective**: Close the tenant-isolation gap on all five Knowledge Engine capabilities (justified independently as a live security fix, not merely an AI-readiness prerequisite), then register a single, minimal, read-only AI tool (`knowledge_search`) reusing the existing, unmodified AI tool-invocation and governance chain.

**Problem statement**: Today, any authenticated caller holding the ordinary (non-admin) `knowledge:read` or `knowledge:write` permission can read or write another tenant's knowledge graph, search results, or ingested sources by supplying that tenant's id — reachable right now through the existing desktop Knowledge UI, with no AI involvement required. This is the same class of defect M6.3 and M7.4 fixed elsewhere, but worse in degree (0 of 5 handlers even accept a `principal` parameter, versus "accepted but not applied" in the pre-fix Connector/Document cases) and worse in reachability (already live via desktop, not merely a risk that AI exposure would introduce).

**User value**: Tenants gain assurance their indexed knowledge (documents, sources, search results) is not readable or writable by other tenants — a baseline data-isolation guarantee, not a new feature. Separately, AI Studio agents gain the ability to ground answers in a tenant's own indexed knowledge via `knowledge_search`, the same kind of capability RAG-style assistants are expected to have.

**Architectural value**: A third, independent proof that the AI tool-invocation/governance chain built in M7.2-M7.4 generalizes across engines with zero chain-level changes — and the natural, evidence-justified point (per §6's AI-tool-coherence finding) to introduce a small shared registration helper before a fourth engine's tools make the copy-paste pattern genuinely unmanageable.

### 8. Scope

- Add `principal: SecurityPrincipal | None = None` to all 5 Knowledge Engine capability handlers (`search`, `index_source`, `load_pack`, `traverse_graph`, `list_nodes`) and make `principal.tenant_id`, when present, authoritative over any caller-supplied tenant identifier — mirroring the established M6.3/M7.4 pattern exactly.
- Register exactly one new AI tool: `knowledge_search` (read-only, `is_mutation=False`, wraps `kortex.knowledge.query.search`, no approval required).
- Adversarial tenant-isolation tests for all 5 hardened capabilities (cross-tenant fail-closed), mirroring `test_document_tenant_isolation_dispatch.py`'s structure.
- A canonical AI-tool vertical slice (`knowledge_search` invoked via the real dispatch chain, tenant-isolation proven through the AI path specifically), mirroring `test_ai_document_tool_invocation.py`'s structure (minus the mutation/approval-flow tests, since there is no mutation tool in scope — see §9).
- Opportunistic, evidence-justified AI-tool-registration hygiene: a small shared idempotent-registration helper (replacing 3 near-identical copy-pasted `if not tool_registry.has_tool(...)` blocks) and the missing `register_document_ai_tools` boot-time idempotency unit test in `test_kernel_bootstrap.py` (a gap this session's own investigation surfaced) — done as part of W3's natural touch of that file, not as a separate refactor project.

### 9. Non-Scope

- **No mutation-class Knowledge AI tool** (e.g., an AI-triggered `knowledge_index_source`) in this milestone. Unlike M7.3/M7.4, there is no clear existing product evidence (acceptance scenario, desktop feature request, prior planning artifact) that an AI agent autonomously indexing new knowledge sources is wanted yet — adding one now would be exactly the "invent a capability to look complete" anti-pattern this session's instructions warn against. Flagged as an open question in §17, not silently included or silently dropped.
- **No AI tool for `graph.traverse`/`list_nodes`.** `search()` is the one capability with a clear, obvious AI use case (grounding chat answers). Graph traversal/node listing are desktop-browse primitives today; nothing suggests an AI agent needs them directly, and M7.4 already established the precedent of NOT exposing every hardened capability as a tool (`profile.list` was fixed and exposed to Kernel dispatch but deliberately not turned into an AI tool).
- **No desktop UI change.** The existing `document-knowledge` feature's calls are unaffected in shape (the `tenant_id` field/param stays on the wire for backward compatibility, only its authority changes when a verified `principal` is present); AI Studio's existing generic tool-call rendering already covers `knowledge_search` with zero UI-side code, exactly as it did for M7.3/M7.4.
- **No fix to the already-known, already-documented `secret.get` or `agent.cancel`/`.status`/`.list` gaps.** Reconfirmed present this session (§5), but out of scope — neither blocks nor is blocked by the Knowledge work, and bundling unrelated security fixes into one milestone would blur certification and rollback boundaries.
- **No Marketplace write path, no business-module work, no RecipeEngine boot-wiring.** All three were investigated and ruled out in §6 as substantially larger, riskier, new-subsystem undertakings unsuited to this milestone slot.
- **No standalone "AI Tool Registry refactor" milestone.** The hygiene work in §8 is small and absorbed into W3; a larger refactor (e.g., a formal tool-category taxonomy, a declarative tool-catalog file) is deferred until there is a fourth engine's evidence that the copy-paste pattern has become a genuine liability, not before.

### 15. Test Strategy

**Unit tests**: `principal.tenant_id` derivation on each of the 5 hardened handlers; permission enforcement (401/403 gates, already proven by existing `test_knowledge_capability_dispatch.py` — extend, don't replace); `knowledge_search` `ToolDefinition` schema validation; idempotent tool registration.

**Integration tests**: real Kernel dispatch for all 5 hardened capabilities with a real token/principal; `knowledge_search` through the real `AIToolInvoker` → `KernelToolExecutionPort` → `CapabilityDispatcher` chain.

**Adversarial tests**: cross-tenant read attempt on `search`/`traverse_graph`/`list_nodes` (tenant B token, tenant A's real node/query data) — expect empty/not-found, never tenant A's real result; cross-tenant write attempt on `index_source`/`load_pack` (tenant B token, tenant A id embedded in payload) — expect fail-closed, never a write landing in tenant A's partition; the same cross-tenant proof repeated through the AI tool path specifically for `knowledge_search`.

**E2E / vertical slice**: `AI Studio → AgentOrchestrator → ToolRegistry → AIToolInvoker → KernelToolExecutionPort → CapabilityDispatcher → KnowledgeEngine.search → persistence`, proven with a real tenant, immediate dispatch (no approval needed), and a real cross-tenant negative case through the same path. No mutation/approval vertical slice is needed unless §17's open question resolves toward including one.

No specific test counts are projected — the prior two milestones' actual counts (7 adversarial + 6 vertical-slice for Document) suggest a similar order of magnitude (5 capabilities × ~1-2 adversarial tests each, plus a smaller vertical slice given only one AI tool is in scope), but fabricating an exact number here would not be evidence-based.

### 17. Open Technical Questions

1. **Should M7.5 include a mutation-class Knowledge AI tool (e.g., `knowledge_index_source`)?** Why it matters: M7.3/M7.4 both shipped one read + one mutation tool; shipping only a read tool here is a deliberate departure from that cadence. Evidence available: no acceptance scenario, prior planning artifact, or desktop feature signals a need for AI-triggered ingestion yet; `index_source`/`load_pack` are real, tenant-isolable capabilities that COULD be exposed safely once W1 lands. Recommendation: defer — ship read-only in M7.5, revisit only if a concrete product scenario emerges. What would change the recommendation: a specific user story (e.g., "let the agent ingest a pasted URL as a new source") surfacing from product direction.
2. **Does `document-knowledge`'s desktop `tenantId` ever come from anything other than the authenticated principal's own session?** Why it matters: determines whether W1 is purely additive-safe for the desktop or requires a companion desktop check. Evidence available: not yet gathered (flagged, not assumed, per §14). Recommendation: a 10-minute grep at implementation start, before W1 is considered complete. What would change the recommendation: finding a code path where `tenantId` is user-selectable (e.g., an admin cross-tenant view) — none is currently known to exist.
3. **Should the AI-tool-registration hygiene work (§8/W3) be scoped exactly as described, or deferred entirely to a later milestone?** Why it matters: it's real, evidence-justified debt, but is not blocking. Evidence available: 3 engines' worth of copy-pasted registration functions, one already-slipped test-coverage asymmetry (§1). Recommendation: include the small helper + backfilled test now, since W3 touches the same file anyway and the marginal cost is near-zero; do not expand into a larger refactor (category taxonomy, catalog file) without a fourth engine's evidence. What would change the recommendation: if implementation reveals the helper would require touching the two already-shipped registration functions in a risky way — in which case, defer entirely rather than destabilize working code for a hygiene nice-to-have.
