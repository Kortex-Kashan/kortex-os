# KORTEX Browser — Known Limitations

**Status**: Living document — updated every phase. Established Browser-B0.

## As of Browser-B3 (Profiles + Persistent Sessions — implemented)

- **No automated test exercises a live, real WebView2 profile directory end-to-end** — same OD-B5 environment limitation as B1/B2 (`tauri::test`'s `MockRuntime` crashes this environment when combined with `unstable`). Unlike B1/B2, most of B3's NEW logic (path containment, registry CRUD, PID-liveness locking, audit logging) is pure Rust and IS automated-tested without needing a live `Window`/`Webview` — only "does a real WebView2 instance actually persist real cookies/localStorage to the resolved directory across a real app restart" remains a manual-verification gap.
- **`icacls`-based ACL restriction is baseline OS-user isolation only, not full AppContainer-SID isolation.** Explicitly scoped this way (D26/OD-B12) — a stronger isolation pass, matching `python_exec/windows_boundary.py`'s AppContainer+Job-Object model, remains open for a future hardening phase if this risk class ever warrants it.
- **No disk-quota or exhaustion protection** against a hostile page filling a profile's WebView2 storage (OD-B10). No existing KORTEX precedent for this anywhere in the codebase; explicitly deferred, not a B3 deliverable.
- **No encryption-at-rest** for profile directories (OD-B11). No existing precedent for encrypting an opaque WebView2-owned folder; explicitly deferred.
- **Profile lifecycle audit events are local-only** (a structured, append-only JSON-Lines file under the profiles root), not routed through the backend's real `AuditManager`/`UniversalAuditEntry` — an explicit, documented interim decision (D23), since Browser IPC has no backend hop at all today. Superseded once Browser gains a real capability-dispatcher hop (likely Browser-B5).
- **The audit log is a single, shared file across all tenants** on one installation, not split per tenant. Every entry is itself tenant-labeled, and the profile *directory* hierarchy already discloses tenant existence to anyone with local filesystem access to this installation, so sharing one log file does not meaningfully increase that exposure — documented explicitly (D23), not silently assumed.
- **A narrow, residual TOCTOU race remains in stale-lock recovery**: if two processes both decide the identical lock is stale in the exact same instant, both may locally believe they hold it (the atomic rename-over ensures only one write actually wins on disk). WebView2's own folder-exclusivity (confirmed live in the OD-B9 preflight) is the independent second layer that still prevents actual concurrent access to the profile directory in that narrow window.
- **`USERNAME`-based ACL grants may not resolve correctly on a domain-joined machine** in every configuration — `icacls` is given a bare username, not an explicit `DOMAIN\user` form; works correctly on this development machine and the common local-account case, not independently verified against every possible domain configuration.
- **No session/open-tab restore across app restarts** — explicitly out of scope for B3 (a UI/session-state feature, distinct from profile *storage*, which is what B3 delivers; cookies/localStorage do persist across restarts once a profile's directory is reused, independent of whether the open-tabs list is restored).
- **No profile reset (clear data, keep identity), import/export, or backup** — all explicitly out of scope for B3 per the architecture gate; only create/rename/delete/list/open/close are implemented.
- Everything listed under "As of Browser-B2" below that B3 didn't address (no capability/governance layer, `kortex.browser.view` declared-but-unenforced) remains true.

**Resolved by Browser-B3 (2026-09-26)**: real per-tenant profile isolation (was: one shared, non-persisted `"default"` profile for the whole process lifetime — see B1/B2's own entries below); the B1/B2 legacy `browser-profiles/default` directory, if one exists on a machine that already ran B1/B2 with a live UI session, is automatically quarantined (never deleted, never assigned to a tenant) on first B3 launch.

## As of Browser-B2 (Browser UI — implemented)

- **No automated test for the new raw WebView2 COM code.** `GoBack`/`GoForward`/`CanGoBack`/`CanGoForward` and the `NavigationStarting`/`NavigationCompleted` event handlers backing `loading` have zero automated coverage — same OD-B5 environment limitation as Browser-B1's lifecycle code (no live `Window`/`Webview` can be constructed in this environment's `cargo test`). An independent adversarial review verified the binding usage itself against the actual `webview2-com-sys` source (signatures, out-pointer handling, handler lifetime, thread/apartment correctness) and found it correct — that verification is by source inspection, not execution.
- **The new `#[cfg(not(windows))]` fallback path was not confirmed by an actual Linux compiler run**, but was confirmed by an exhaustive manual audit (every occurrence of every Windows-only identifier in the file traced to a `#[cfg(windows)]`-gated item, with no gap found) — a stronger form of local verification than the earlier attempted `cargo check --target x86_64-unknown-linux-gnu`, which failed on a pre-existing, unrelated system-library gap (`glib-sys`/`gobject-sys` need Linux system headers this Windows machine doesn't have) before reaching this crate's own code. See `browser_decision_log.md` OD-B6 — first real compiler confirmation is still this repository's own CI, next time this branch is pushed.
- **A newly-created surface's very first navigation can miss its `loading = true` transition.** `register_navigation_loading_handlers`'s registration is dispatched fire-and-forget to the main thread from `create_surface`, which returns to the frontend without waiting for that registration to actually land — if the initial page's `NavigationStarting` fires first, `loading` can stay `false` through the first load. Cosmetic (first-load-only; every subsequent navigation is unaffected), found by adversarial review, deliberately **not fixed** in the Browser-B2 review-fix pass (out of that pass's explicit scope) — remains open for a future phase if it proves worth the added complexity of making registration synchronous.
- **No visual/interactive confirmation of real back/forward, loading-indicator, resize, or tab-switching behavior.** Verified only by unit/component tests against mocked APIs and by manual code review of the actual WebView2/COM call shapes — a human running the real app is the remaining verification step, same as Browser-B1.
- ~~**All Browser-B2 tabs share one process-lifetime, non-persisted profile**~~ **RESOLVED by Browser-B3 (2026-09-26)** — see that section above. (Historical note: this "default" profile directory was, in fact, already accumulating real persistent WebView2 data across app restarts even in B1/B2, since nothing ever cleared it — "non-persisted" described the lack of profile *management*, not the underlying directory's actual on-disk behavior. B3's legacy-quarantine logic accounts for this.)
- **Tab surfaces are parked off-screen at a fixed coordinate when inactive, not truly hidden.** Functionally correct (invisible, no user-facing effect) but relies on the parked coordinate never being reachable by window resizing/maximizing; not something Tauri's `Webview` API offers a dedicated "hide" primitive for as of this pinned version.
- **No Browser Policy enforcement point yet** — unchanged from Browser-B1; today's security posture rests entirely on Tauri's own static ACL (verified sound for the "arbitrary website gets zero KORTEX capabilities" baseline).
- Everything listed under "As of Browser-B1" below that Browser-B2 didn't address (no persistent profiles, no capability layer, no AI agent) remains true.

**Resolved by the Browser-B2 post-review fix pass (2026-09-25)**: two real orphan-surface defects (unmount-during-create, destroy-failure-untracking) and one error-swallowing gap in `useBrowserTabs.ts` — see `browser_decision_log.md` D17.

## As of Browser-B1 (WebView2 Browser Runtime Foundation — implemented)

- **No automated test exercises a live `Window`/`Webview`, real or mocked.** `tauri::test::MockRuntime` (needed for this) crashes every test binary at startup in this environment when combined with the `unstable` feature this crate requires (`STATUS_ENTRYPOINT_NOT_FOUND`); root cause not isolated. See `browser_decision_log.md` D12/OD-B5. `browser_runtime.rs`'s tests cover pure logic only (path sanitization, id/error serialization).
- **No interactive/visual confirmation that a WebView2 surface renders real content.** The real production binary was launched and observed to start cleanly, but no tool in this session can drive the resulting native OS window's UI — a human running the app and clicking through Open/Navigate/Reload/Close is the remaining verification step. See `docs/architecture/browser_b1_implementation_report.md` §Tests.
- **Fixed placement/size** for the single Browser-B1 proof-of-concept surface — no dynamic docking to a DOM element's layout yet (Browser-B2).
- **No back/forward navigation** — wry's stable `Webview` API has no session-history methods; deferred (D11).
- **No persistent profiles** — `resolve_profile_directory`/`default_profile_root` are a minimal stand-in for `BrowserProfileStore` (Browser-B3).
- **No Browser Policy enforcement point yet** — today's security posture rests entirely on Tauri's own static, build-time ACL (verified sound for the "arbitrary website gets zero KORTEX capabilities" baseline — see `browser_security_model.md` §4), not the dynamic, origin/profile-aware policy layer Browser-B4 will add.
- **`kortex.browser.view` is declared but not yet enforced**, matching every other `DEFAULT_APPLICATIONS` entry's current state (a pre-existing, repository-wide condition, not specific to Browser).

## As of Browser-B0 (documentation-only phase)

- **No code exists yet.** Every claim about "the cleanest integration seam" in `browser_architecture.md` is a recommendation based on read-only investigation, not a verified implementation — B1 may surface constraints this audit didn't anticipate.
- **Windows-only V1.** WebView2 is a Windows Evergreen/Chromium runtime; a future macOS/Linux desktop build (already a deferred item in `docs/release/RELEASE_CANDIDATE_READINESS.md`) will need a second `IKortexBrowserRuntime` adapter before Browser is available cross-platform. Not a defect — a scoped, known V1 gap (see ADR-0019 §5).
- ~~**Tauri multi-webview support is unverified.**~~ **Resolved by the Browser-B1 preflight (2026-09-25).** `Window::add_child()` exists in the pinned `tauri = "=2.11.5"` (`window/mod.rs:1129`) and supports exactly the embedded-child-webview architecture `browser_architecture.md` §2.3 describes. The remaining, more precise limitation: `add_child` is gated behind the `unstable` Cargo feature, which this repo's `Cargo.toml` does not currently enable — a required, low-risk, one-line prerequisite for B1 (see `browser_decision_log.md` D7, `docs/architecture/browser_b1_preflight_report.md`). Tauri v2's capability-file ACL schema scoping a grant to a specific *child-webview label* (vs. only a window label) remains unverified (`browser_decision_log.md` OD-B4).
- **No sandboxing model designed yet for the browser runtime process itself.** The existing Python execution sandbox (AppContainer + Job Object, `python_exec/windows_boundary.py`) is a separate system solving a different problem (arbitrary Python code execution) and does not transfer directly to a WebView2 host process; B1/B4 must determine what process-level isolation, if any, KORTEX layers on top of what WebView2 itself already provides.
- **No profile storage construct exists yet.** `browser_security_model.md` §10 identifies that KORTEX's current persistence model (SQL rows + AAD encryption) cannot represent an opaque WebView2 user-data folder; a new `BrowserProfileStore` must be designed in B3, not assumed to already fit an existing facade.
- **No prompt-injection sanitizer exists anywhere in the codebase.** Flagged in `browser_security_model.md` §11 as the one component this project cannot get "for free" from existing machinery; it must be designed and adversarially tested (B6, B9) before any AI-observable browsing ships.
- **`CapabilityPalette`'s capability allowlist is currently hardcoded.** `CURATED_CAPABILITY_NAMES` (`CapabilityPalette.tsx:13-17`) will need explicit `kortex.browser.*` entries added in B5/B8 — trivial, but not automatic.
- **The existing `devBrowserBridge` is not usable prior art for the untrusted-content isolation problem.** It solves a different, dev-tooling-only problem (see `browser_security_model.md` §4); B4 must design the native-bridge boundary from first principles.
- **Gate-numbering / phase-numbering ambiguity in the wider repository is a pre-existing condition, not something this project resolves.** `.kortex/roadmap.md`'s own reconciliation pass (uncommitted as of this audit) already flags unresolved "Gate 3/5/6" numbering and a "Phase A" section unrelated to this project's "Browser-B" numbering — see `browser_decision_log.md` D2.

## Anticipated (not yet confirmed) limitations for later phases

- B7's "controlled authentication window" concept has no existing UI precedent in this codebase to build from (today's OAuth flow opens the OS's external browser, not an embedded controlled surface) — genuinely new UX and security design required, not an adaptation of existing code.
- B9's adversarial testing scope (prompt injection, hostile websites, navigation escapes) has no existing red-team harness in this repository to reuse; tooling for it is not yet identified.
