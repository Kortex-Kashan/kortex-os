## AI Execution Control Plane Hardening

### 1. Executive Summary

**COMPLETE.** `AIOrchestrationEngine._on_approval_decided` — the only path that resumes an approved AI-originated mutation in production (a human decision always arrives asynchronously via the durable `workflow.approval.decided` event, never through the synchronous `resume_agent` API) — called `AgentOrchestrator.resume_task(...)` directly, without ever acquiring a `TenantConcurrencyThrottler` agent slot, unlike both synchronous entry points (`orchestrate_agent`, `resume_agent`), which already wrap their own resume/run calls in it. Every mutating AI tool built so far (Connector's `connector_send_action`, Document's `document_generate`) therefore had its approval-resume traffic bypass the per-tenant concurrent-agent-workflow cap the rest of the control plane enforces. This is now fixed: the resume call is wrapped in the same, single, authoritative throttler already owned by the engine — no second throttling mechanism was introduced.

Two small, tightly related hygiene gaps identified in the same investigation were also closed: the boot-time AI-tool-registration idempotency test that existed for Connector but not Document or Knowledge (`test_kernel_bootstrap.py`), and a telemetry asymmetry where a successful tool invocation's already-computed latency was recorded only into `AIDiagnostics` directly, publishing no domain event and incrementing no exporter counter — unlike the failure/denial paths, which do both.

No Marketplace, business-module, desktop, Connector/Document/Knowledge business-logic, Rust/Tauri, or general telemetry-redesign work was touched, per the milestone's explicit scope.

### 5. Root Cause

Verified directly by reading `backend/src/kortex/engines/ai/engine.py`:

```python
# orchestrate_agent (line 984) and resume_agent (line 1035) — SYNCHRONOUS:
async with self._throttler.acquire_agent_slot(task.tenant_id):
    result = await self._agent_orchestrator.run_task(...)   # or .resume_task(...)

# _on_approval_decided (line 1501, before this fix) — ASYNCHRONOUS:
resumed_result = await self._agent_orchestrator.resume_task(
    task=record.task, resume_token=record.resume_token,
    approved_tool_calls=record.pending_tool_calls,
)
# no throttler acquisition anywhere in this handler
```

`_on_approval_decided` is the *only* code path that resumes an approved AI-originated mutation in production. This is not a tenant-isolation/data-leak defect — `get_task(task_id, tenant_id)` already fails closed on a tenant mismatch, and the resumed `task` object comes from the durably-stored, originally-validated record, never from the event payload — but it is a genuine concurrency-control gap: the per-tenant cap `TenantConcurrencyThrottler` exists specifically to enforce does not apply on the busiest resume path in the whole control plane.

A secondary, more precise finding during W3 investigation (superseding the planning report's initial, slightly imprecise framing): the successful-completion branch of `invoke_tool` (`engine.py` line ~1161) *did* already record latency into `AIDiagnostics.record_tool_invocation(status="SUCCESS", latency_ms=...)` directly — latency itself was never literally discarded. The real gap was architectural asymmetry: unlike `emit_tool_failed`/`emit_tool_denied` (both of which publish a domain event *and* increment an exporter counter *and* record diagnostics, via `AITelemetryEmitter`), a successful completion bypassed `AITelemetryEmitter` entirely, publishing no event and incrementing no counter — an observability blind spot for the single most common outcome.

### 6. W1 — Concurrency-Control Fix

**Old path**: `_on_approval_decided`'s APPROVED branch called `self._agent_orchestrator.resume_task(...)` with zero throttle involvement.

**Why it bypassed throttling**: `_on_approval_decided` was added (M6.2-4) as a subscriber to the generic `workflow.approval.decided` event, independently of `orchestrate_agent`/`resume_agent`'s later-added (M12) throttle wrapping — the two code paths were never unified, and nothing enforced that a new resume entry point had to acquire the same slot.

**Chosen fix location**: wraps only the APPROVED branch's `resume_task` call (not the entire handler) in `async with self._throttler.acquire_agent_slot(tenant_id):`. Verified via Graphify (§3) that `AgentOrchestrator` itself has no throttler dependency, ruling out wrapping inside `AgentOrchestrator.resume_task` (Option C) — that would double-acquire against `resume_agent`'s own wrapping for calls that go through that path. Wrapping the *entire* handler (Option A) was also rejected: the REJECTED branch's `cancel_task` call must never consume a slot (proven by a dedicated test, §8/Test G), and the whole-method approach would have incorrectly gated it too. The chosen scope (Option B, the exact call site) is the lowest layer that closes the gap without any risk of double acquisition.

**Acquisition/release lifecycle**: `acquire_agent_slot` (unmodified) is a fail-fast `@asynccontextmanager` — it raises `TenantQuotaExceededError` immediately if the tenant is already at `max_concurrent_agents` (default 5), never waits or queues; release happens in a `finally` block, guaranteed regardless of what happens inside the `async with` body (success, an unrelated exception from `resume_task`, or nothing at all if acquisition itself failed).

**Saturated-tenant behavior (resolves the planning report's open question §23)**: a `TenantQuotaExceededError` is caught specifically (not by the handler's pre-existing generic `except Exception`) and the task is deliberately left `PAUSED_FOR_APPROVAL` rather than cancelled — the approval decision itself is already durably recorded by the Workflow Engine (this handler neither created nor consumes it), so cancelling would incorrectly discard a validly-approved action. This is safe under the handler's own pre-existing idempotency guarantee (a no-op once the task's status is no longer `PAUSED_FOR_APPROVAL`): a later redelivery or operator-triggered replay of the exact same event can still resume the task once a slot frees, with zero risk of double execution — proven directly by test (§8).

```

    ↓ kortex.ai.agent.orchestrate / .resume (unchanged)
AgentOrchestrator (unchanged — confirmed no throttler dependency, §3)
    ↓
[human approves] → workflow.approval.decided event
    ↓
AIOrchestrationEngine._on_approval_decided
    ↓ get_task(task_id, tenant_id) — fails closed (unchanged)
    ↓ action_fingerprint check (unchanged)

    ↓
AgentOrchestrator.resume_task — CAS-guarded (unchanged)
    ↓
Real tool dispatch (Connector / Document / Knowledge, unchanged)
    ↓ on SUCCESS: [M7.6-W3 FIX] AITelemetryEmitter.emit_tool_completed(...)
```

No new component. No new abstraction. `TenantConcurrencyThrottler` is the sole, unmodified, authoritative tenant-concurrency mechanism, now applied uniformly across all three task-resumption/execution entry points.
