# KORTEX OS — M7.3 Implementation Report
## AI Studio ↔ Connector Engine Integration

---

### 1. Executive Summary

**COMPLETE.** AI Studio agents can now safely invoke the existing, production-hardened Connector Engine through two governed AI tools — one read-only (dispatches immediately), one mutating (requires human approval through the existing Workflow Approval Queue, resumes automatically on decision). No new engine, credential store, approval mechanism, HTTP client, or audit system was built: this milestone is additive wiring across the Connector Engine, Security Engine, AI Engine, and desktop Connectors app, closing three concrete, evidence-based gaps identified during M7.3 planning:

1. The production HTTP driver existed but was never registered on the real boot path.
2. `ConnectorProfileManager` had full CRUD methods, but only `get_profile` was exposed as an authorized Kernel capability — nothing let a tenant create, list, or delete a connection.
3. The AI Engine's `ToolRegistry` was always constructible but nothing had ever populated it — zero AI tools existed anywhere in the platform before this milestone.

Two real regressions were found and fixed along the way (both pre-existing tests that asserted the connector driver registry starts empty on production boot — an assumption this milestone's own W1 objective correctly overturns). One design correction was made mid-implementation after the schema-shape assumption in the original plan didn't match the real `ConnectorEngine.execute_action(request, principal=None)` signature.

### 6. Architecture

The final, real dispatch path — no component below the Kernel boundary is new:

```
AI Studio Chat
    ↓ kortex.ai.agent.orchestrate (existing, M7.2)
AgentOrchestrator (existing)
    ↓ LLM proposes a tool call
AIToolInvoker (existing) → ToolRegistry.get_tool() (existing type, newly populated)
    ↓ validates arguments against parameters_schema (existing)
KernelToolExecutionPort.execute_tool (existing)
    ↓ kernel_bridge.invoke_capability(...)
CapabilityDispatcher.dispatch (existing) — authenticate → authorize (RBAC) → derive tenant
    → invoke handler
ConnectorEngine.execute_action (existing, M2/M6.3) — principal.tenant_id authoritative
    ↓
ConnectorPipeline (existing) — validate → authenticate (secret_resolver) → rate-limit → dispatch → audit
    ↓
HttpRestConnectorDriver / DummyConnectorDriver (existing, now registered at boot — M7.3-W1)
    ↓
External service
```

The only things that did not exist before this milestone: two `ToolDefinition`s registered into `ToolRegistry` (M7.3-W4), three Kernel capabilities wrapping already-existing `ConnectorProfileManager` methods (M7.3-W2), one Kernel capability wrapping the already-existing `SecretStore.put_secret` (M7.3-W3), and the driver-registration call itself (M7.3-W1).

### 7. Connector Integration

- **W1 — Driver registration** (`kernel_bootstrap.py`, new `register_production_connector_drivers()`): registers `DummyConnectorDriver` and `HttpRestConnectorDriver` after `kernel.boot()` (registration requires `READY`/`RUNNING` engine state). Idempotent — checks `list_drivers()` before registering each, so a second call against the same engine instance is a no-op rather than raising `ConnectorDriverError`.
- **Existing SSRF/timeout/redirect protections**: untouched. `HttpRestConnectorDriver`'s own source was not modified at all — only its *registration* changed, and its existing adversarial test suite (`test_http_connector_driver.py`) was re-run unmodified as part of full-suite certification (§19).

### 8. AI Tool Architecture

Two `ToolDefinition`s (`kernel_bootstrap.register_connector_ai_tools()`, called once at boot against `ai_engine.tool_registry`):

| Tool | `canonical_capability` | `is_mutation` | Gate |
|---|---|---|---|
| `connector_read_status` | `kortex.connector.action.execute` | `False` | none — dispatches immediately |
| `connector_send_action` | `kortex.connector.action.execute` | `True` | `DurableAIApprovalPolicy` (existing, unmodified) |

**Schema shape — the one real design correction made during implementation**: both tools' `parameters_schema` nests `profile_id`/`action_type`/`payload`/`request_id` under a top-level `request` object, because `ConnectorEngine.execute_action(self, request, principal=None)` takes exactly one parameter named `request`, and the Kernel dispatcher splats a capability's parameters as `handler(**parameters)`. This is not a new convention — it's the identical shape `ExternalExecutionManager` already uses to reach this same capability (`parameters={"request": ActionRequest(...)}`, proven in the pre-existing `test_external_execution_vertical_slice.py`). The original plan (Pass 2 of the planning report) assumed flat top-level fields; that assumption was wrong and was corrected once the real signature was inspected, per the master prompt's own instruction to trust the actual code over the plan.

`action_type` is pinned via JSON Schema `const` per tool (`"FETCH"` / `"SEND"`) so the model cannot use the read-only tool to smuggle a mutating action type past the tool-level `is_mutation` classification that `DurableAIApprovalPolicy` keys off. `profile_id` is left caller-supplied — tenant isolation is enforced one layer down by `ConnectorEngine.execute_action`'s existing principal-authoritative tenant binding, which a schema-level constant would only duplicate (and `ToolRegistry` is a single, process-wide catalog, not per-tenant, so a schema constant couldn't scope it per-tenant anyway).

`request_id` was a required field neither the original plan nor the first implementation pass accounted for (`ActionRequest.request_id` has no default) — added to the schema, described to the model as "a unique identifier you generate for this request."

### 9. Profile Lifecycle

Three new Kernel capabilities on `ConnectorEngine`, all following the exact `execute_action`/`get_profile` principal-authoritative tenant pattern already established in M6.3-1:

| Capability | Wraps | Permission | New validation added |
|---|---|---|---|
| `kortex.connector.profile.register` | `ConnectorProfileManager.register_profile` | `connector:write` | Rejects an unregistered `driver_id` via `registry.get_driver_by_id` — a profile could otherwise register successfully and only fail later, at execution time |
| `kortex.connector.profile.list` | `ConnectorProfileManager.list_profiles` | `connector:read` | — |
| `kortex.connector.profile.delete` | `ConnectorProfileManager.delete_profile` | `connector:write` | `ConnectorProfileManager.delete_profile` takes no `tenant_id` (never needed one before this capability existed) — ownership is verified first via the already-tenant-scoped `get_profile`, which raises `ConnectorProfileNotFoundError` (masked identically to "doesn't exist") if the caller's tenant doesn't own it, before any deletion is attempted |

### 10. Credential Lifecycle

One new capability, `kortex.security.secret.put` (`SecurityEngine.put_secret_capability`), wrapping the already-existing `SecretStore.put_secret`. New: the `security:secret:write` permission (deliberately distinct from `security:read`, which already gates the read-only `secret.get`); principal-authoritative tenant derivation (a gap the pre-existing `secret.get` capability still has and this milestone does not touch — flagged in §22); and — closing a real, pre-existing audit gap — firing `SecuritySecretModifiedEvent`, whose class existed but had never been published by any code path before this capability.

Rotation is `secret.put` called again (`SecretStore.put_secret` is already an upsert) — no separate rotate/list capability was added. `secret.delete` was not added: nothing in this milestone's UI or acceptance scenario needs it (a connection's credential becomes unreachable, not deleted, when its profile is deleted — see §18's known limitation).

### 11. Approval Flow

Zero new code. `connector_send_action`'s `is_mutation=True` is the only signal `DurableAIApprovalPolicy` needs — the exact same policy, the exact same `DurableApprovalManager` queue, and the exact same `ApprovalQueue.tsx` UI (already labels AI-originated requests, M7.2) that governs every other AI-originated mutation. Approve → `_on_approval_decided`'s existing APPROVED branch → `AgentOrchestrator.resume_task` → real `ConnectorEngine.execute_action` dispatch. Reject → `cancel_task`, zero dispatch.

### 12. Tenant Isolation

Every new capability follows the uniform, pre-existing pattern (verified, not assumed): `principal.tenant_id` — set by the Kernel from the caller's verified session token — overrides any caller-supplied `tenant_id` before any tenant-scoped read/write. Adversarially tested (§19): a tenant B agent supplying tenant A's exact (guessed) `profile_id` gets `EXECUTION_ERROR`, never tenant A's real driver response; a tenant B write-permitted principal attempting to delete tenant A's profile by guessed id gets `ConnectorProfileNotFoundError`, masked identically to a nonexistent profile; tenant B cannot list tenant A's profiles.

### 13. RBAC

New permission strings: `connector:write` (already existed, reused for the two new mutating profile capabilities), `connector:read` (already existed, reused for `profile.list`), `security:secret:write` (genuinely new — write access to arbitrary tenant secrets is more sensitive than `security:read`, so it is independently grantable/revocable, not folded into an existing permission). A fresh install's bootstrap-created admin (M7.1) receives it automatically via the existing dynamic capability-union grant; an admin bootstrapped before M7.3 needs it granted manually — the same manual step already required for any RBAC permission on this platform (no permission-provisioning API exists, a pre-existing gap not introduced or fixed here).

### 14. Secret Handling

- Never returned in plaintext by any capability response (`secret.put`'s response carries only `secret_handle`/`tenant_id`/`updated_at_utc`).
- Never appears in the AI tool schema, prompt, or arguments — `secret_handle` is an opaque reference the tool never even needs to see; the actual secret is resolved entirely inside `ConnectorPipeline`, below the AI Engine's boundary.
- Never appears in conversation history — `scrub_secrets_from_text` (pre-existing, M6) redacts any dict key matching `secret`/`token`/`api_key`/etc. in every tool result before it enters agent step history; a connector result rides through this unchanged.
- Never appears in audit records — the Kernel dispatcher's own `sanitize_for_persistence` redacts the `plaintext` parameter generically; `put_secret_capability`'s own explicit audit call never includes it either.
- Never persisted client-side — the desktop credential field is a write-only password input; `ConnectorProfile` (what the frontend ever reads back) carries no secret-value field.

### 15. SSRF Verification

`HttpRestConnectorDriver`'s existing SSRF hardening (IP-pinning, private/reserved/loopback/link-local blocking, obfuscated-IP detection, no redirects, body-size caps) was not modified. Its existing adversarial test suite ran unmodified as part of full-suite certification (§19) — no new SSRF surface was introduced, since the AI path reaches the identical driver instance through the identical `ConnectorPipeline`, just via a different caller (`AIToolInvoker` instead of `ExternalExecutionManager`).

### 16. Audit Behavior

No new audit mechanism. Every capability call in this milestone is already audited generically by the Kernel dispatcher's `_audit_execution`. The one concrete, deliberate addition is `put_secret_capability` firing `SecuritySecretModifiedEvent` — closing a documented, pre-existing gap (the event class existed since before M7.3; nothing had ever published it).

### 17. Idempotency Analysis

**Idempotency guarantee**: an AI-originated mutating connector dispatch triggered via a `workflow.approval.decided` event executes at most once, even under duplicate event delivery.

**Evidence**: `test_ai_connector_tool_invocation.py::test_duplicate_approval_decided_event_does_not_dispatch_the_connector_action_twice` — captures the real event a real approval decision publishes and re-delivers that exact object a second time directly to `AIOrchestrationEngine._on_approval_decided`, proving no second dispatch occurs. This holds because of two independent, pre-existing (not new) guards: `_on_approval_decided` no-ops whenever the task's status is no longer `PAUSED_FOR_APPROVAL` (its own docstring: "idempotent no-op either way"), and `AgentOrchestrator.resume_task` additionally CAS-claims the persisted record (`PAUSED_FOR_APPROVAL → RESUMING`) before proceeding. Neither guard is connector-specific — they protect every AI-originated mutation identically, so this milestone required a test, not a fix.

**Remaining limitation**: this covers duplicate *event delivery* only. `ConnectorEngine.execute_action` itself carries no idempotency key of its own on the AI-tool path (unlike `ExternalExecutionRequest.idempotency_key`'s `UniqueConstraint(tenant_id, idempotency_key)` on the Workflow-triggered path) — acceptable because the AI-tool path never retries a completed dispatch; there is no code path that would attempt a second live call for the same resumed task. Flagged, not silently worked around.

### 18. Desktop Changes

Extended the existing `/connectors` app (no new application, matching the plan's explicit reasoning: no Settings app exists, and the Connectors app was already the natural, permission-gated extension point) with a "Connections" tab alongside the pre-existing read-only "Drivers" tab:

- `types.ts` — `ConnectorProfile`, `CreateConnectionPayload` (no secret-value field on either).
- `api.ts` — `listConnectorProfiles`, `registerConnectorProfile` (sequences `profile.register` then, only if a credential was entered, `secret.put` under a handle derived from `profileId`), `deleteConnectorProfile`.
- `hooks/useConnectorProfiles.ts` — query + two mutation hooks, mirroring `useSchedules.ts`'s established convention.
- `components/ConnectionsTab.tsx` — list/create/delete UI. Credential field is `type="password"`, never prefilled, never re-displayed after save. A single installed driver auto-selects itself (both a UX convenience and what makes the create-flow test deterministic without needing to drive the Radix `Select` popover open).

**Known limitation, desktop**: `deleteConnectorProfile` does not also delete the associated secret (`SecretStore` has no cascade-delete concept, and no `secret.delete` capability was added — see §10). A deleted connection's credential becomes unreachable (nothing can resolve its handle without a profile referencing it) but not actively purged. Flagged as acceptable for this milestone, not fixed.

### 20. E2E Scenarios

All four proven at the real dispatch/HTTP boundary in `test_ai_connector_tool_invocation.py`, mirroring the depth of the pre-existing `test_ai_durable_approval_vertical_slice.py`:

1. **Normal read**: agent proposes `connector_read_status` → real `ConnectorEngine`/`DummyConnectorDriver` dispatch → result recorded in durable conversation history.
2. **Governed mutation**: agent proposes `connector_send_action` → real durable approval ticket → real human decision via `kortex.workflow.approval.decide` → real event-driven automatic resume → real dispatch → result in history.
3. **Rejection**: real decision REJECTED → task cancelled → zero dispatch → zero history.
4. **Cross-tenant**: agent under tenant B naming tenant A's exact profile_id → fails closed, never tenant A's real result.
5. (Additional, beyond the master prompt's minimum) **Duplicate-event idempotency** — §17.

### 22. Known Limitations

1. `kortex.security.secret.get` (pre-existing, not touched by M7.3) still does not derive tenant identity from a verified principal — it trusts a caller-supplied `tenant_id` directly. This milestone's own new `secret.put` does not have this gap (built correctly from the start), but the asymmetry is a real, pre-existing issue worth a dedicated fix outside this milestone's scope.
2. `kortex.ai.agent.cancel`/`.status`/`.list` (flagged by M7.2's own report, not touched by M7.3 either) still do not correct a caller-supplied `tenant_id` from the principal. `useAgentStatus` polling a connector-invoking agent makes this capability more heavily used than before, but introduces no new exploitable path — the desktop UI never supplies an attacker-controlled `tenant_id` today.
3. No `secret.delete` capability — a deleted connection's credential is orphaned, not purged (§18).
4. No `profile.update` (edit-in-place) — a tenant re-registers (upsert) rather than patches individual fields; matches the minimal-surface guidance and the absence of any evidence a tenant needs partial edits.
5. `request_id` on both AI tools is LLM-generated per call, not server-injected — a deliberate, minimal choice (§8) rather than modifying the shared, generic tool-invocation pipeline for one tool family's convenience.
