### 5. The Critical Discovery: Dispatch Never Coerced Dict Parameters Into Declared Pydantic Models

Empirically probing `kortex.ai.response.generate` over a real HTTP call (a plain JSON `request` object, exactly what the desktop's `invokeCapability` sends) crashed with `AttributeError` — `generate_response`'s `request: LLMRequest` parameter received a raw `dict`, not an `LLMRequest` instance, because `CapabilityDispatcher._invoke_handler` (`core/dispatch.py`) never coerced JSON-object parameters into the Pydantic model types handlers actually declare. This is not new to M7.2 — `tests/unit/test_knowledge_capability_dispatch.py` already had a test named `test_search_capability_is_broken_over_the_real_dict_based_ipc_path`, previously left broken and explicitly documented as "deliberately NOT exercised," with a docstring anticipating exactly this class of fix ("a coercion wrapper"). Without fixing this, no capability in this milestone — `generate`, `orchestrate`, `resume`, `invoke_tool`, the new `conversation.history.get` — could ever be reached from the real desktop transport; the entire M7.2 objective was unreachable without it.

**Fix** (`core/dispatch.py`): two new functions, `_resolve_model_target` (resolves `BaseModel`, `Optional[BaseModel]`, `list[BaseModel]`, and their PEP 604 `X | None` equivalents from a handler's real, `eval_str=True`-resolved annotation) and `_coerce_model_parameters` (walks the handler's declared parameters and `model_validate`s any dict-shaped argument whose declared type is a `BaseModel`, leaving already-live instances and genuinely dict-typed parameters untouched), called once in `_invoke_handler` immediately before `handler(**call_kwargs)`. This is a general, platform-wide root-cause fix, not scoped to AI capabilities — it also fixes `kortex.knowledge.query.search` as a documented side effect, and that test was updated from "is broken" to "now works" rather than left stale.

### 6. The Second Discovery: Agent-Orchestrated Turns Were Never Durably Recorded

Reading `orchestrate_agent`/`resume_agent` in full (not just their signatures) revealed that **only `generate_response` calls `AIMemoryManager.append_history`** — the agent-orchestration path (`AgentOrchestrator.run_task`/`resume_task` in `agent.py`) never has, and by design never can: `agent.py` carries a hard, AST-enforced import quarantine (`NEVER import kortex.engines.ai.memory`) precisely because `IAgentContextPort` already hides that subsystem behind a read-only interface.

Since the desktop's Chat tab sends **every** message through `kortex.ai.agent.orchestrate` (the only capability that can produce the `PAUSED_FOR_APPROVAL`/tool-call semantics Option B requires — there is no client-side guessing about which capability a given message needs, matching the master prompt's "don't auto-classify intent" instruction), and since the new `kortex.ai.conversation.history.get` capability is the *only* sanctioned way to rehydrate a transcript, this gap meant conversation-recovery-after-restart would have silently failed for every agent-driven turn — the exact scenario W10 requires proving.

**Resolution** (`engine.py`, additive, `engine.py`-only — `agent.py`'s quarantine is untouched): a new private helper, `_record_agent_conversation_turn(task, result)`, called at the end of `orchestrate_agent`, the end of `resume_agent`, and inside `_on_approval_decided`'s `APPROVED` branch (which calls `AgentOrchestrator.resume_task` directly, bypassing the `resume_agent` facade — so the fix could not live in one place alone). It records a turn only for a terminal, non-paused result carrying a `final_response`, by constructing a synthetic `LLMRequest`/`LLMResponse` pair (`prompt=task.goal`, `text_content=result.final_response`) and calling the same, unmodified `append_history` method `generate_response` already uses — reusing the existing mechanism, not redesigning it. A rejected/cancelled task (no `final_response` exists) deliberately records nothing. Failure is handled identically to `generate_response`'s own precedent: caught, logged, and surfaced via the existing `AgentExecutionResult.degraded` field rather than discarding an already-completed turn.

This is flagged here prominently, not silently: it is a genuine, deliberate extension of two previously-certified M6.2 capabilities' behavior, made only because the M7.2 objective is provably unreachable without it (a chat surface that cannot survive a restart is not "conversational completion"), verified end-to-end through the real event-driven auto-resume chain (§10), and does not touch `agent.py`'s own quarantined internals.

### 11. Security Verification

1. **Tenant identity never trusted from the caller** (§2.2): `get_conversation_history` follows the identical unconditional-override pattern as `invoke_tool`/`generate_response`/`orchestrate_agent`. Proven directly by `test_get_conversation_history_forces_principal_tenant_not_spoofed_caller_tenant` (a principal from tenant B reading/writing under a caller-claimed tenant A id is silently corrected to B) and by the real-HTTP round-trip test in `test_ai_studio_api_http.py` (deliberately wrong `tenant_id` in the request body, correct tenant's history returned regardless).
2. **RBAC**: `kortex.ai.conversation.history.get` requires `ai:read`; proven at the real HTTP boundary (401 no-auth, 403 missing-permission, 200 authorized).
3. **Desktop never resumes anything itself**: `chat-api.ts` has no function that calls `kortex.ai.agent.resume` — grep-verifiable, not merely a convention. Every resolution the desktop observes came from the server's own event-driven `_on_approval_decided` handler.
4. **No second approval-decision surface**: `ToolCallCard.tsx` has exactly one action, a navigation call. No approve/reject/delegate code path exists anywhere under `features/ai-studio/`.
5. **XSS**: `MessageBubble.tsx` renders `message.content` as plain JSX text (React's default escaping) — no `dangerouslySetInnerHTML`, no `eval`, no HTML-string construction anywhere in the new UI.
6. **Client-side storage**: exactly one `localStorage` key per (tenant, user), holding only an opaque conversation id — see §8. No message content, no tokens, no credentials.
7. **New backend write path scoped correctly** (§6): `_record_agent_conversation_turn` is only reachable from `orchestrate_agent`/`resume_agent`/`_on_approval_decided`, all of which already had tenant-corrected `task.tenant_id` by the time it runs; it introduces no new external input surface, only reuses the existing, already-tenant-safe `append_history` method.
8. **Known, pre-existing, deliberately out-of-scope finding, re-confirmed and now more directly relevant**: `kortex.ai.agent.cancel`/`status`/`list` (`cancel_agent_task`/`get_agent_task`/`list_agent_tasks` in `engine.py`) still take no `principal` parameter and therefore still do not correct a caller-supplied `tenant_id` — the identical gap the M7.2 planning report flagged as "not automatically in scope unless directly touched." It was not touched this session (per the planning report's own explicit instruction), but `useAgentStatus` is now a real, shipped consumer of `kortex.ai.agent.status`, so this gap is worth flagging with elevated visibility for a future milestone: today, the desktop UI itself never supplies an attacker-controlled `tenant_id` to this call (it always comes from the authenticated identity), so this feature introduces no new exploitable path — but any caller reaching this capability directly (bypassing the UI) with a spoofed `tenant_id` and otherwise-valid RBAC could still read or cancel another tenant's agent task. Recommended for the next AI-engine hardening pass.
