## 5. Architecture Discovery — the exact seam being closed

Two independently-complete pipelines exist on `cd51df5` and share the same two choke points (`CapabilityDispatcher` for execution, `DurableApprovalManager` for mutation governance) without ever having been connected to each other:

```
Pipeline 1 (exists, M6.3/M6.4):
  Workflow Engine → ExternalExecutionManager → kortex.connector.action.execute
    → ConnectorEngine → ConnectorPipeline → HttpRestConnectorDriver → external service
    (mutations gated by DurableApprovalManager)

Pipeline 2 (exists, M7.2):
  AI Studio Chat → kortex.ai.agent.orchestrate → AgentOrchestrator → LLM proposes tool calls
    → ToolRegistry lookup (EMPTY — nothing registered) → AIToolInvoker → KernelBridgeAdapter
    → CapabilityDispatcher  ← the exact same dispatcher Pipeline 1 uses
    (mutations gated by DurableAIApprovalPolicy → same DurableApprovalManager as Pipeline 1)
```

**The seam**: `ToolRegistry` is empty. Nothing tells the AI Engine that `kortex.connector.action.execute` exists, what its schema is, or whether a given connector action is a mutation. Once one `ToolDefinition` is registered, `AIToolInvoker.invoke_tool` → `KernelBridgeAdapter.invoke_capability` → `CapabilityDispatcher.dispatch` is **mechanically identical** to `ExternalExecutionManager`'s own call path — same tenant-derivation-from-principal pattern, same generic Kernel-level audit, same secret-scrubbing (`scrub_secrets_from_text`, already applied to every tool result before it enters conversation history), same approval queue and its already-tested AI-requester labeling in `ApprovalQueue.tsx`.

This means the plan is **additive wiring, not new architecture** — no new engine, no new approval mechanism, no new audit mechanism, no new secret store.

## 6. AI Tool Integration — concrete design

**`ToolDefinition` for the reference connector action** (registered in `AIOrchestrationEngine`'s bootstrap, alongside the existing capability registrations):

```python
ToolDefinition(
    name="fetch_reference_connector_status",
    description="Fetch status from the reference external connector (read-only).",
    canonical_capability="kortex.connector.action.execute",
    parameters_schema={
        "type": "object",
        "properties": {
            "profile_id": {"type": "string", "const": "<reference-profile-id>"},
            "action_type": {"type": "string", "const": "FETCH"},
            "payload": {"type": "object"},
        },
        "required": ["profile_id", "action_type"],
    },
    is_mutation=False,
    timeout_seconds=30,
)
```

A second `ToolDefinition` for a mutating action (`action_type: "SEND"` or `"PUSH"`, `is_mutation=True`) proves the approval path. **`profile_id` is pinned via a JSON Schema `const`** (not LLM-choosable) so the model can only target the one profile this milestone provisions — this is the concrete mechanism preventing "tool argument injection" (Threat T4 in §11) at the schema level, before the request ever reaches the Connector Engine's own tenant/profile checks.

- **No schema-translation framework is built.** For this milestone's one reference connector, the `parameters_schema` is hand-authored (matching the brief's own guidance: "prefer 1–3 carefully selected operations," not a generalized schema generator). A generic "any `ConnectorProfile` → any LLM tool schema" translator is explicitly deferred — nothing in the evidence base shows a second connector is imminent, and building one now would be exactly the "speculative abstraction for future flexibility" rule 13 forbids.
- **What the agent sees**: tool `name`, `description`, `parameters_schema` (profile_id/action_type/payload shape only). **What it never sees**: `secret_handle`, the resolved secret value, or any credential — these are resolved server-side inside `ConnectorPipeline`, entirely below the capability boundary the AI Engine ever touches.
- **Mutation → approval**: `DurableAIApprovalPolicy` already checks `ToolDefinition.is_mutation` generically — zero changes needed there. Setting `is_mutation=True` on the second tool is sufficient; the existing `WAITING_APPROVAL` → `ApprovalQueue.tsx` (already labels AI-originated requests, tested in M7.2's W8) → decide → resume chain requires no new code.
- **Result → conversation**: `ToolResult.to_context_entry` already truncates and secret-scrubs before the result enters agent step history, and `_record_agent_conversation_turn` (M7.2) already durably persists the terminal turn. No changes needed.

## 7. Credential Architecture — the provisioning gap

`SecretStore` (AES-256-GCM, tenant+handle-scoped) is correct and sufficient as-is. The gap is **provisioning**: `put_secret`/`delete_secret` are called only internally today (AI system-credential bootstrap). This milestone adds exactly one new capability:

- **`kortex.security.secret.put`** — wraps `SecurityEngine.secret_store.put_secret(handle, tenant_id, plaintext)`. `required_permissions=["security:secret:write"]` (a new permission string — no role currently has it, so it must be granted to the `admin` role as part of this milestone's setup, following the exact dynamic-RBAC-grant pattern M7.1's bootstrap capability already established). Tenant is derived from the verified principal, never the caller-supplied value (the uniform pattern every other engine already follows).
- **Fires the existing, currently-dead `SecuritySecretModifiedEvent`** (operation=PUT) — closing the audit gap identified in Pass 1 §3.B with zero new event-schema work, just the missing call site.
- **`kortex.security.secret.delete`** is deferred unless the reference connector's disconnect flow needs it (§10) — `delete_secret` already exists on `SecretStore`; adding its capability wrapper is a ~10-line mechanical twin of `secret.put` if needed.
- **No OAuth infrastructure, no token-refresh scheduler, no OS-keyring-on-desktop path** — the reference connector uses a static API-key-shaped credential (rule 12 of the brief forbids building OAuth speculatively; nothing in the evidence base shows a near-term connector that needs it).

## 11. Security Threat Model

| Threat | Attack Surface | Mitigation (existing or new) | Test |
|---|---|---|---|
| T1 Credential theft | Secret exfiltration via tool output, conversation history, audit log, or exception | Existing `scrub_secrets_from_text` (M6 AI engine) scrubs tool output/history; `sanitize_for_persistence` (Kernel dispatcher) redacts audit context; `SecretStore` never returns plaintext outside `ConnectorPipeline`'s in-process resolution | New: adversarial test asserting a resolved secret value never appears in `ToolResult`, conversation history, or audit records for the reference connector |
| T2 Tenant escape | Cross-tenant profile/secret/tool-call access | Existing, proven pattern: `principal.tenant_id` overrides caller-supplied value at every layer (Connector, Security, AI engines) | New: adversarial test — tenant B's agent cannot invoke tenant A's connector profile even if it guesses `profile_id` (mirrors `test_connector_tenant_isolation_dispatch.py`'s existing pattern) |
| T3 Connector impersonation | A malicious tool-call response claims to be from the connector but isn't | `ConnectorPipeline` is the sole path to `HttpRestConnectorDriver`; `AIToolInvoker` never accepts a caller-supplied result, only what `execution_port.execute_tool` returns from a real dispatch | Existing dispatch-integrity tests apply unchanged |
| T4 Tool argument injection | LLM-crafted `profile_id`/`payload` escaping the intended target | `parameters_schema`'s `const` on `profile_id` (§6) + Connector Engine's own tenant/profile validation as defense-in-depth | New: test that a schema-violating or wrong-`profile_id` tool call is rejected before dispatch |
| T5 SSRF | Connector action reaching an internal/private address | Already fully handled by `HttpRestConnectorDriver`'s existing SSRF hardening (Pass 1 §3.A) — unaffected by which caller (Workflow or AI) reaches it | Existing `test_http_connector_driver.py` SSRF suite applies unchanged; no new surface introduced |
| T6 Secret leakage through AI | Secret appearing in a prompt, system instruction, or LLM-visible schema | `parameters_schema` never includes `secret_handle` or any credential field (§6); secret resolution happens entirely inside `ConnectorPipeline`, below the AI Engine's visibility | New: static assertion the `ToolDefinition`'s schema contains no secret-shaped field; existing prompt-sanitization tests (M5) apply unchanged |
| T7 Secret leakage through audit | Plaintext secret in an audit record for `secret.put` | `sanitize_for_persistence`'s existing `SENSITIVE_KEY_NAMES` set already includes `secret`/`credential`/`api_key` — the new capability's parameters are audited through the same generic dispatcher path | New: test asserting `kortex.security.secret.put`'s audit record never contains the submitted plaintext |
| T8 Unauthorized mutation | A mutating connector tool call executing without approval | `DurableAIApprovalPolicy` already fails closed on unknown/missing `is_mutation` (Pass 1 §3.D); the mutating `ToolDefinition` sets `is_mutation=True` explicitly | New: end-to-end test — mutating tool call pauses for approval, does not execute until `APPROVED` |
| T9 Replay/duplicate execution | A resumed or retried tool call executing twice | Existing `ExternalExecutionManager`-pattern idempotency (`UniqueConstraint(tenant_id, idempotency_key)`) — **note**: `AIToolInvoker`'s path does not currently generate/pass an idempotency key the way `ExternalExecutionManager` does; this is a genuine open question for W5 (§13) rather than a pre-solved item | New: verify whether `AgentOrchestrator`'s resume path could double-invoke a tool call, and if so, thread an idempotency key through (small, scoped fix, not a redesign) |
| T10 Revoked credential reuse | A tool call succeeding after `secret.delete` | `ConnectorPipeline`'s existing fail-closed behavior when `secret_resolver` returns nothing / raises for a deleted handle | Existing pipeline tests cover this; new test confirms it holds when the caller is an AI tool, not just a Workflow step |

## 12. Audit Architecture

No new audit *mechanism*. Every capability call in this plan already routes through the Kernel dispatcher's generic `_audit_execution`, which redacts sensitive keys automatically. The one concrete addition is wiring the already-defined `SecuritySecretModifiedEvent`/`SecuritySecretAccessedEvent` into `secret.put`'s handler (§7) — closing a documented gap, not building new infrastructure.

## 13. Error Model

Reuses the existing error hierarchies unchanged: `ConnectorException` subtypes (invalid credentials, timeout, rate-limited — already modeled in `exceptions.py`) surface through `ToolResult`'s existing error-shape handling (already proven for Workflow-triggered failures); `AIBootstrapError`/`AgentValidationError` for policy/registration errors. **No new error types are introduced.** The one genuinely new failure mode is a schema-rejected tool call (T4) — handled by the existing `LLMOutputParser`/`ToolValidationError` path, which already raises cleanly rather than silently failing through.

## 14. Reference Connector Recommendation

Confirmed from Pass 1: **no new driver.** One `ConnectorProfile` using the existing `HttpRestConnectorDriver`, targeting one low-risk endpoint, with exactly two actions:

1. **`FETCH`** (read, `is_mutation=False`) — proves discovery → tool call → dispatch → result → conversation history, with zero approval friction.
2. **One mutating action** (`SEND`/`PUSH`, `is_mutation=True`) — proves the approval-gated path reaches the same `DurableApprovalManager` queue the Workflow Engine already uses, end to end, from an AI-originated request.

If no suitable low-risk external test target exists in the target environment, `DummyConnectorDriver` (already built, already registered-capable) is an acceptable substitute for the automated test suite specifically — but at least one manual/E2E verification pass should use the real `HttpRestConnectorDriver` against a genuine (even if sandboxed/internal) HTTP endpoint, since `DummyConnectorDriver` alone would not prove the SSRF-hardened driver path is actually reachable from an AI tool call.

## 24. Definition of Done

1. `HttpRestConnectorDriver` and `DummyConnectorDriver` are present in `ConnectorEngine.list_drivers()` on a fresh production boot, with no manual registration step.
2. A tenant admin can create, list, and delete a `ConnectorProfile` via Kernel capabilities, each enforcing tenant isolation identical to `execute_action`'s existing proven pattern (verified by an adversarial cross-tenant test).

4. An AI Studio conversation can invoke the reference connector's read action and receive a real result from `HttpRestConnectorDriver`, with zero approval friction.
5. An AI Studio conversation invoking the reference connector's mutating action pauses for approval, appears correctly labeled in the existing Workflow Approval Queue, and only executes after approval — verified end-to-end, not just at the unit level.
6. A rejected mutating tool call results in zero dispatch to the external service.
7. A user authenticated as tenant B cannot list, read, or invoke tenant A's connector profile or credential through any capability, including via an AI agent tool call — verified adversarially.
8. No credential value appears in any AI prompt, tool schema, conversation history record, audit record, or exception message — verified by a dedicated test asserting this, not by code inspection alone.
9. Full backend/desktop/Rust/TypeScript regression suites pass at parity with the M7.2 baseline (2,352/519/45/clean), modulo the same pre-existing `tzdata` failure and known load-flake category already documented in the M6.4/M7.1/M7.2 reports.
