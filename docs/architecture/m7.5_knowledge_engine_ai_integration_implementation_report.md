### 1. Executive Summary

**COMPLETE.** All five Knowledge Engine capabilities previously had no tenant-isolation enforcement whatsoever — none of their handlers accepted a `principal` parameter, so every caller-supplied `tenant_id` was trusted as-is. This was not a hypothetical AI-exposure risk: it was already reachable in production through the existing desktop Knowledge UI. All five handlers (`search`, `traverse_graph`, `list_nodes`, `index_source`, `load_pack`) now derive tenant identity from the Kernel-verified `principal.tenant_id`, adversarially proven through real Kernel dispatch. One new, deliberately read-only AI tool (`knowledge_search`) was registered into the AI Engine's `ToolRegistry`, proven end-to-end through the real `AgentOrchestrator → ToolRegistry → AIToolInvoker → KernelToolExecutionPort → CapabilityDispatcher → KnowledgeEngine` chain — the third engine (after Connector, M7.3, and Document, M7.4) to reach this chain with zero chain-level changes.

Three things were discovered during implementation that were not part of the original plan:

1. **A real, verified, independent bug**: `KnowledgeEngine._REGISTERED_CAPABILITIES` (the engine's own self-reported capability list) was missing `kortex.knowledge.graph.list`, even though it was correctly registered with the Kernel at boot. Fixed alongside the tenant-isolation work since the same method needed touching regardless.
2. **A necessary, narrow model change**: the master implementation prompt requires the AI tool schema to never accept `tenant_id` at all. `KnowledgeQuery.tenant_id` was a required field with no default, which would have made construction from an LLM-supplied dict (which never includes `tenant_id`) fail before the tenant-derivation fix ever got a chance to run. Fixed by giving it a `"default"` fallback value — an exact mirror of `document.models.BindingContext.tenant_id: str = "default"`'s already-established precedent, not a new pattern.
3. **A stale-but-already-resolved historical concern**: `list_nodes`'s own docstring claimed `search()`'s `KnowledgeQuery` parameter was "confirmed to raise `AttributeError` over the real IPC path." Investigation (per the master prompt's explicit Enum/request-coercion audit requirement) found this was true only *before* M7.2's dispatch-coercion fix, and that fix's own regression test (`test_search_capability_now_works_over_the_real_dict_based_ipc_path`) already proves the concern is resolved. No new coercion fix was needed — verified, not assumed.

A fourth, opportunistic improvement was made: the `if not tool_registry.has_tool(...): tool_registry.register_tool(...)` idempotency guard — copy-pasted five times across `register_connector_ai_tools`/`register_document_ai_tools` — was extracted into a small shared `_register_tool_if_absent` helper and applied to all three registration functions (the two already-shipped ones, plus the new one), closing a coherence gap the M7.5 planning report's own AI-tool-surface investigation identified.

### 6. Tenant-Isolation Changes

All five changes follow the identical `principal.tenant_id`-authoritative pattern established in M6.3 (Connector Engine) and M7.4 (Document Engine) — the Kernel dispatcher injects its own verified identity into any handler parameter literally named `principal`; when present, it overrides any caller-supplied tenant identifier before any tenant-scoped operation proceeds.

| Handler | Capability | Before | After |
|---|---|---|---|
| `search(query, principal=None)` | `kortex.knowledge.query.search` | `query.tenant_id` (frozen model, caller-supplied) used as-is | `principal is not None` → `query = query.model_copy(update={"tenant_id": principal.tenant_id})` before `search_hybrid()` |
| `traverse_graph(node_id, tenant_id, max_hops, principal=None)` | `kortex.knowledge.graph.traverse` | bare `tenant_id: str` param used as-is | `principal is not None` → `tenant_id = principal.tenant_id` before `self._graph.traverse(...)` |
| `list_nodes(tenant_id, principal=None)` | `kortex.knowledge.graph.list` | bare `tenant_id: str` param used as-is | same override, before `self._graph.list_nodes(tenant_id)` |
| `index_source(source_id, tenant_id, principal=None)` | `kortex.knowledge.source.index` | bare `tenant_id: str` param used as-is | same override, before `provider.ingest(tenant_id)` and record persistence |
| `load_pack(pack, principal=None)` | `kortex.knowledge.pack.load` | `pack.tenant_id` (mutable model, caller-supplied) used as-is | `principal is not None` → `pack = pack.model_copy(update={"tenant_id": principal.tenant_id})` before `_pack_manager.load_pack(pack)` |

**Model change required for `knowledge_search`'s schema constraint (§7)**: `KnowledgeQuery.tenant_id` changed from `Field(..., min_length=1)` (required, no default) to `Field(default="default", min_length=1)` — mirrors `BindingContext.tenant_id: str = "default"` exactly. This fallback value is never read by real search logic on the production dispatch path (it is always overridden by `principal.tenant_id` first); it exists solely so a dict lacking `tenant_id` still constructs successfully. No existing caller was affected — every pre-existing direct-construction call site already supplies a real `tenant_id` explicitly.

### 8. AI Tool Architecture

One tool, `knowledge_search` (`kortex.knowledge.query.search`, `is_mutation=False`, no approval, `timeout_seconds=30.0`), registered by the new `register_knowledge_ai_tools(tool_registry)` function in `kernel_bootstrap.py`, called at boot immediately after `register_document_ai_tools`.

**Schema shape**: mirrors `search(self, query: KnowledgeQuery, principal=None)`'s real single-parameter signature — the tool call's arguments dict must contain a top-level `query` key to land on that parameter (`handler(**parameters)` splatting, the same rule the connector/document tools' schemas already conform to). Inside `query`: `query_id` (required, LLM-generated, mirrors `request_id`'s established convention), `query_text` (required, the actual search text), `max_results` (optional, bounds result size).

**Deliberately excluded from the schema, and why**:
- `tenant_id` — the master implementation prompt explicitly forbids it (§10: "The AI tool must NOT accept: tenant_id"). Tenant identity comes exclusively from `principal`.
- `filters` — spec-reserved, unimplemented, no code path reads it; exposing it to the LLM would suggest a capability that doesn't exist.
- `entity_types`/`trust_states`/`as_of` — all have safe model defaults; `trust_states` in particular defaults to excluding unverified `SOURCE_EVIDENCE`/`AI_CANDIDATE` content, a default this tool preserves rather than giving the LLM an unevidenced lever to loosen.

**Deliberately not built**: any mutation-class Knowledge tool (`knowledge_index_source`, `knowledge_load_pack`). The planning report (§9/§17 Q1) found no product evidence for AI-triggered knowledge mutation yet, and the master prompt's own scope guardrails agree ("Do NOT automatically add mutation tools... unless the repository evidence and explicit milestone scope require them"). Left as an explicit, undecided open question for a future milestone, not silently added or foreclosed.

### 9. Production Registration

`register_knowledge_ai_tools(ai_engine.tool_registry)` is called in `build_and_boot_kernel()` (`kernel_bootstrap.py`) immediately after `register_document_ai_tools`, after `kernel.boot()` (registration requires the AI Engine's `ToolRegistry` to already exist). Idempotent via the shared `_register_tool_if_absent` helper (§13).

### 14. Result / Content Security

Investigated per the master prompt's explicit §15 audit requirement, since Knowledge search results can carry substantially more text than a Connector response:

- **What reaches the AI tool output / conversation history**: the raw `KnowledgeQueryResult` (matching nodes, relationships, records), passed through unchanged by `KernelToolExecutionPort`/`AIToolInvoker` — the same generic, unmodified pass-through every other tool's output already goes through.
- **What bounds it**: the existing, generic `ToolResult.to_context_entry()` — `MAX_TOOL_OUTPUT_CHARS` (50,000 char) truncation, `scrub_secrets_from_text`, a 64 KiB hard byte ceiling, delimiter neutralization. No new Knowledge-specific truncation or scrubbing was built, per the master prompt's explicit instruction not to invent a new mitigation without an actual, evidenced gap — this backstop already applies generically. Proven, not assumed: `test_large_knowledge_search_result_is_bounded_before_entering_conversation_history` constructs a 100-node, ~200,000-character result and confirms the context entry is truncated and marked `TRUNCATED`.
- **What gets persisted**: durable conversation history stores the tool result through the same existing mechanism every other tool result uses — no new persistence path.
- **Whether metadata leaks tenant information**: `KnowledgeNode`/`KnowledgeRecord` objects carry their own `tenant_id` field, but by construction (once W1 is in place) a caller only ever receives results already scoped to their own tenant — the embedded `tenant_id` is always the caller's own, never a cross-tenant leak. Not a new finding; identical reasoning to how Connector/Document tool results already carry their own tenant-scoped identifiers.

### 16. Known Issues

- The load-sensitive flake category (§15.2) remains a standing, environmental characteristic of this test environment under full-suite contention — not fixed by this or any prior milestone, and out of scope to fix here (it is not specific to any one test; it has already surfaced on at least three different tests across different milestones' certification runs).
- `KnowledgeQuery.tenant_id`'s new `"default"` fallback (§6) is, by design, never meant to be read by real search logic — if a future capability change ever removed the `principal`-override step from `search()`, a caller omitting `tenant_id` would silently search under the literal string `"default"` rather than failing loudly. This is an accepted trade-off (identical to `BindingContext.tenant_id`'s existing precedent, not a new risk class this milestone introduced), not a defect.
- The two already-known, already-documented gaps (`kortex.security.secret.get`, `kortex.ai.agent.cancel`/`.status`/`.list`) remain unfixed and out of scope, unchanged from M7.2/M7.3.
