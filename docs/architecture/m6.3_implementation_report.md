### 2. Starting State (verified fresh at M6.3 planning time)

- Full backend suite: 2254 passed, 1 pre-existing failure (`test_cron_schedule_respects_configured_timezone`, a tzdata/timezone-environment issue), 2 skipped.
- `ExternalExecutionManager` existed (M5.4) with real dispatch, retry/backoff, timeout enforcement, and a transactional outbox, but:
  - `ConnectorProfile` had no `tenant_id` at all — any caller with `connector:execute` could reach any tenant's connector profile and secret by guessing its `profile_id`.
  - No test anywhere ever set `ExternalExecutionRequest.target` to a real Connector capability — the wiring was structurally possible but unproven.
  - The WAITING_APPROVAL branch created an approval ticket and returned; nothing in the codebase ever resumed or cancelled that execution once a human decided the ticket.
  - The approval ticket it created never carried a requester identity, correlation ID, or action fingerprint.
  - `ExternalExecutionModel` had only a non-unique index on `(tenant_id, idempotency_key)`.
  - No recovery path existed for an execution stranded in RUNNING by a crash.

### 3. M6.3-1 — Connector Trust-Boundary Fix (prerequisite, commits `7941543`, `98c3f01`)

Added `tenant_id` to `ConnectorProfile`/`ConnectorProfileModel`; `ConnectorProfileManager.get_profile`/`list_profiles` now filter and mask cross-tenant lookups as "not found" (enumeration-resistant); `ConnectorEngine.execute_action`/`get_profile` bind the Kernel-verified `principal.tenant_id` as authoritative over any caller-supplied `tenant_id`. 7 new adversarial tests (cross-tenant read/write/secret-leak attempts, RBAC-denial guard) plus repair of 14 pre-existing tests that had implicitly relied on the old, tenant-blind behavior.

### 4. M6.3-2 — External Execution → Connector Wiring (commit `530b039`)

Proved, for the first time, that `ExternalExecutionManager`'s real dispatch path (not the separate `WorkflowStep`/`StepEvaluator` path) reaches a real, registered Connector capability and driver. 2 new integration tests against a real Kernel + ConnectorEngine + DummyConnectorDriver.

### 5. M6.3-3 — Durable Approval Resume/Cancel + Action Fingerprint (commit `4ecba4a`)

- `ExternalExecutionStore`: persists `timeout_seconds`/`retry_policy_json` at creation; added `get_dispatch_context()` to read back everything needed to re-invoke a paused execution.
- `ExternalExecutionManager`: extracted `execute_operation`'s dispatch/retry/timeout loop into `_run_dispatch_and_record()`, shared by both the immediate-dispatch and resume paths against the *same* execution id (no orphaned duplicate records); added `_compute_action_fingerprint()`; the WAITING_APPROVAL branch now threads `principal`/`correlation_id`/`action_fingerprint` into the ticket; added `on_approval_decided()`, an event handler mirroring `AIOrchestrationEngine._on_approval_decided` (M6.2-4) — resumes on APPROVED after re-verifying the fingerprint, cancels on anything else, fails closed on any ambiguity (execution not found, wrong status, missing dispatch context, fingerprint mismatch).
- `WorkflowEngine.decide_approval_request`: `tid` is now derived from the verified `principal` first (D7 hardening — a caller can no longer decide into a tenant other than their own by passing a different `tenant_id` argument); mints a fresh session token for the deciding principal via `issue_token()` (safe because that principal was just verified via `verify_token` in the same request) and publishes it in the `workflow.approval.decided` event payload as `decider_session_token`, so the resumed dispatch authenticates as a real, verified identity instead of forging one; wires the executor's subscription in `initialize()`.
- `ConnectorEngine.execute_action`: now accepts `request` as a plain `dict` in addition to a real `ActionRequest` — discovered mid-implementation that a resumed execution's parameters necessarily come back from JSON persistence as dicts (Kernel dispatch does not coerce dict→pydantic on `**kwargs` handler invocation), so the live and resumed paths previously behaved differently for the exact target this milestone's slice uses.

### 6. M6.3-4 — Idempotency & Replay Protection (commit `f21bf63`)

- `ExternalExecutionModel`: replaced the non-unique index with a real `UniqueConstraint("tenant_id", "idempotency_key")` (NULL keys remain exempt under standard SQL NULL-distinctness — only callers who opt in are protected).
- `ExternalExecutionStore`: added `get_execution_by_idempotency_key()` and `get_stranded_executions()` (RUNNING only).
- `ExternalExecutionManager.execute_operation`: looks up an existing record by idempotency key *before* creating a new one or entering the approval gate — a duplicate of an already-waiting-for-approval request returns the same ticket, not a second one.
- `ExternalExecutionManager.recover_stranded_executions()`: a RUNNING row abandoned by a crash is never blindly auto-resumed (its external side effect may or may not have already landed); it is deterministically failed closed with an actionable error, wired into `WorkflowEngine.start()` alongside the pre-existing workflow-instance hydration scan. WAITING_APPROVAL rows are left untouched — nothing dispatches them until a real decision event arrives.

### 7. M6.3-5 — Canonical Vertical Slice (commit `0ef566d`)

Four cases against a real Kernel/RBAC/DurableApprovalManager/ConnectorEngine: (A) governance denial without `workflow:execute`, (B) approval→REJECTED cancels with no connector call, (C) approval→APPROVED completes with full inspectable trace, (D) cross-tenant attack fails closed on read, decide, and profile substitution. No production code changes — proves M6.3-1..4 already deliver the required behavior.

### 8. Security Verification (HOW verified)

- **Tenant isolation on Connector**: `test_connector_tenant_isolation_dispatch.py` (7 cases) drives real Kernel dispatch across two tenants sharing a role name; cross-tenant profile/secret access is proven masked as "not found."
- **Approval self-approval / cross-tenant decide**: exercised directly — `test_self_approval_denied_for_external_execution_ticket` and vertical-slice Case D — both assert on the real `DurableApprovalManager.submit_decision` guards (pre-existing M6.2-3 code, now proven to apply to external-execution tickets because a real requester identity is now recorded).
- **Action fingerprint tamper resistance**: `test_fingerprint_mismatch_refuses_resume_and_cancels` delivers a forged `workflow.approval.decided` event with a wrong fingerprint directly to `on_approval_decided` and asserts the execution is cancelled, not resumed.
- **Fresh identity on resume, not forged**: verified by inspecting that `_run_dispatch_and_record`'s `session_token` for the resume path comes exclusively from `decider_session_token` (minted server-side from the verified approver principal), never from caller-supplied event data.

### 18. Deferred / Out of Scope

- Approval-ticket **expiry** (`DurableApprovalManager.sweep_expired_requests`) does not publish a `workflow.approval.decided` event — this is a pre-existing gap shared with the AI-approval path (M6.2-4), not introduced or fixed by M6.3. An expired ticket's execution simply remains WAITING_APPROVAL indefinitely (safe — never silently resumed) rather than transitioning to CANCELLED automatically. Flagged, not fixed, per the master brief's scope discipline against unrelated redesigns.
- Concurrent-race idempotency enforcement relies on the DB `UniqueConstraint` as backstop; no explicit `IntegrityError`-catch-and-refetch was added to `save_execution`'s insert path (the lookup-before-create fast path, which the brief specifically named, is what's tested).

### 19. Architectural Deviations

None from the approved plan. The `ConnectorEngine.execute_action` dict-coercion fix was an unplanned but necessary and narrowly-scoped correction discovered while implementing M6.3-3's resume path (a genuine dict-vs-pydantic-object bug, not a redesign).
